## 1. 里程碑信息

### 1.1 目标

实现工作线程层（`worker/`），完成 UI 线程与后台 asyncio 工作线程之间的桥接：
1. 提供 `AsyncWorker` 基础设施：在 `QThread` 后台线程中创建并运行 `asyncio` 事件循环，UI 线程通过 `submit()` 调度协程，支持优雅关闭。
2. 定义全部跨线程信号（工作线程 → UI 方向 12 个、UI → 工作线程方向 10 个），参数类型明确。
3. 实现 `DownloadBridge`：把 UI 控制信号映射到 `Scheduler` 方法，把 `Scheduler` 回调与 `ProgressReporter` 回调转发为 UI 更新信号；并负责应用启动时的断点续传恢复。
4. 实现 `CrawlerBridge`：把 UI 控制信号映射到 `URLParser` / `UserHomeCrawler` / `CookieTester` 调用，把结果转发为 UI 更新信号；支持 `cancel_parse` / `cancel_home_fetch` 通过 `asyncio.Task.cancel` 取消。
5. 配套单元/集成测试，`worker/` 行覆盖率 ≥ 80%。

### 1.3 关键设计约束

- **线程模型严格遵循设计文档 2.3 节**：Qt 主线程跑 UI，后台工作线程跑 asyncio 事件循环；二者通过 Qt 信号/槽（`pyqtSignal`/`Signal`）线程安全通信。
- **asyncio loop 必须在工作线程中创建**：UI 线程不得直接 `asyncio.run`；UI 线程通过 `AsyncWorker.submit(coro)` 把协程调度到工作线程的 loop 中执行。
- **信号参数类型必须明确**：所有 `Signal` 的参数类型在定义处显式声明（如 `Signal(int, str)`、`Signal(list)`），并在文档中标注 list 元素的实际类型。
- **桥接器只做转发，不含业务逻辑**：`DownloadBridge` / `CrawlerBridge` 不实现下载或解析逻辑，只做信号 ↔ 方法的映射与数据结构转换。
- **取消操作用 `asyncio.Task.cancel`**：`cancel_parse` / `cancel_home_fetch` 通过持有对应 `asyncio.Task` 引用并调用 `.cancel()` 实现。
- **进度节流由 v0.0.5 的 `ProgressReporter` 负责**：本里程碑只把 `ProgressReporter.on_progress` 回调桥接到 `progress_updated` 信号，不重复实现节流。
- **优雅关闭**：`AsyncWorker.stop()` 时取消所有未完成的 `asyncio.Task`，等待 loop 清理后退出线程。
- **单向依赖**：`worker/` 依赖 `downloader/`、`crawlers/`、`app/`；不得被下层反向依赖。

#### 1.2 类定义

**`AsyncWorker(QThread)`**

继承自 `PySide6.QtCore.QThread`，在 `run()` 方法中创建并运行 `asyncio` 事件循环。

#### 1.3 成员清单

| 成员 | 签名 | 行为描述 |
|---|---|---|
| `__init__` | `(self, parent: QObject \| None = None) -> None` | 调用 `super().__init__(parent)`；初始化 `_loop: asyncio.AbstractEventLoop \| None = None`、`_loop_ready: threading.Event`（用于等待 loop 在工作线程中创建完成）、`_stop_event: asyncio.Event \| None = None`（loop 内的停止信号）、`_pending_tasks: set[asyncio.Task]`（跟踪已提交未完成的任务） |
| `run` | `(self) -> None`（重写 QThread.run） | 工作线程入口：在当前线程（工作线程）创建 `asyncio.new_event_loop()`，赋值给 `self._loop`；`asyncio.set_event_loop(self._loop)`；`self._loop_ready.set()` 通知 UI 线程 loop 已就绪；创建 `self._stop_event = asyncio.Event()`；调用 `self._loop.run_until_complete(self._stop_event.wait())` 阻塞运行 loop 直到 stop 被调用；退出前调用 `self._cleanup()` 清理 |
| `start` | `(self) -> None`（重写 QThread.start） | 调用 `super().start()` 启动线程；调用 `self._loop_ready.wait(timeout=5.0)` 阻塞等待 loop 在工作线程中创建完成（超时 5 秒，超时抛 `RuntimeError("AsyncWorker loop start timeout")`）；确保 `start()` 返回时 `self._loop` 已可用 |
| `stop` | `(self) -> None` | 优雅关闭：通过 `self._loop.call_soon_threadsafe(self._stop_event.set)` 设置停止信号；等待进行中的任务完成或取消（见 1.4）；调用 `self.wait(timeout=10.0)` 等待线程退出（超时强制 terminate） |
| `submit` | `(self, coro: Coroutine) -> concurrent.futures.Future` | UI 线程调用入口：断言 `self._loop is not None`；通过 `asyncio.run_coroutine_threadsafe(coro, self._loop)` 把协程调度到工作线程的 loop；返回 `concurrent.futures.Future` 供 UI 线程同步等待结果或添加回调；跟踪该 Task 到 `_pending_tasks`（见 1.5） |
| `run_in_thread` | `(self, coro: Coroutine) -> Awaitable` | 从工作线程内部提交协程：断言当前线程是工作线程（`threading.get_ident() == self.currentThreadId()`）；用 `asyncio.ensure_future(coro, loop=self._loop)` 创建 Task；跟踪到 `_pending_tasks`；返回该 `asyncio.Task`（Awaitable） |
| `_cleanup` | `async (self) -> None` | loop 退出前的清理：取消 `_pending_tasks` 中所有未完成的 Task；`await asyncio.gather(*tasks, return_exceptions=True)` 等待取消完成；`self._loop.stop()` 停止 loop |
| `_track_task` | `(self, task: asyncio.Task) -> None` | 把 task 加入 `_pending_tasks` 集合；通过 `task.add_done_callback(self._untrack_task)` 注册完成回调 |
| `_untrack_task` | `(self, task: asyncio.Task) -> None` | task 完成回调：从 `_pending_tasks` 移除该 task |

#### 1.4 优雅关闭流程（`stop()`）

```
stop():
  1. 若 self._loop is None 或 self._stop_event is None → 直接 return（未启动）
  2. self._loop.call_soon_threadsafe(self._stop_event.set)
     — 在工作线程的 loop 中设置停止信号，使 run() 中的 run_until_complete 返回
  3. self.wait(timeout=10.0) — 等待 QThread.run() 结束
     - run() 结束前会调用 _cleanup()：
       a. 取消 _pending_tasks 中所有未完成的 task（task.cancel()）
       b. await asyncio.gather(*cancelled_tasks, return_exceptions=True)
       c. loop.stop()
  4. 若 self.wait() 超时（线程未退出）→ self.terminate() 强制终止（最后手段，记录日志）
```

#### 1.5 任务跟踪机制

- `submit()` 和 `run_in_thread()` 创建的 `asyncio.Task` 都通过 `_track_task()` 加入 `_pending_tasks` 集合
- task 完成时通过 `add_done_callback` 触发 `_untrack_task()` 从集合移除
- `stop()` 时 `_cleanup()` 能拿到所有未完成的 task 进行取消
- 注意：`submit()` 用 `run_coroutine_threadsafe` 返回的是 `concurrent.futures.Future`，需通过其内部的 `asyncio.Task` 引用跟踪（`run_coroutine_threadsafe` 内部会创建 Task 并绑定到 loop）

#### 1.6 线程安全要点

| 操作 | 线程 | 安全性保证 |
|---|---|---|
| `start()` 中等待 loop 就绪 | UI 线程 | `threading.Event` 跨线程同步 |
| `submit(coro)` | UI 线程 | `asyncio.run_coroutine_threadsafe` 是线程安全的官方 API |
| `run_in_thread(coro)` | 工作线程 | `asyncio.ensure_future` 在同线程调用，安全 |
| `stop()` 设置停止信号 | UI 线程 | `loop.call_soon_threadsafe` 线程安全 |
| `_cleanup()` | 工作线程 | 在 loop 内执行，安全 |
| `_pending_tasks` 集合读写 | UI 线程（submit）+ 工作线程（_cleanup） | UI 线程的 `submit` 通过 `call_soon_threadsafe` 间接写，实际写发生在工作线程；`_track_task` / `_untrack_task` 都在工作线程执行，无竞态 |

#### 1.7 关键常量

| 常量 | 值 | 说明 |
|---|---|---|
| `LOOP_READY_TIMEOUT` | `5.0` | 等待 loop 就绪的超时秒数 |
| `STOP_TIMEOUT` | `10.0` | `stop()` 等待线程退出的超时秒数 |

#### 2.4 信号连接约定

- 所有信号连接使用 `Qt.QueuedConnection`（跨线程默认即 Queued），确保槽在工作线程的 loop 中执行。

#### 3.6 Cookie 全池失效触发机制

- v0.0.5 的 `Scheduler` 在下载过程中收到 `CookieInvalidError`（来自 v0.0.3 的 `HttpClient`）时，若 `HttpClient.check_all_cookies_invalid()` 返回 True，则触发 `on_all_cookies_invalid` 回调。
- 本里程碑 `DownloadBridge._connect_scheduler_callbacks` 中把该回调桥接到 `cookie_invalid` 信号。
- 若 v0.0.5 的 `Scheduler` 未直接暴露 `on_all_cookies_invalid` 回调，本里程碑约定通过 `Scheduler.__init__` 新增 `on_all_cookies_invalid: Callable[[], None] \| None = None` 参数（需 v0.0.5 配合调整，或在桥接器内通过 HttpClient 的回调间接连接——具体方式在实施时与 v0.0.5 接口核对后确定，文档中预留此回调入口）。

#### 3.7 断点续传恢复流程

应用启动时（v0.0.7 的 `main.py` 装配阶段）调用：

```
download_bridge.init_scheduler(concurrency)   # 启动 Scheduler loop
download_bridge.restore_pending_tasks()       # 恢复 pending/paused 任务
```

`restore_pending_tasks` 内部通过 `async_worker.submit(scheduler.restore_pending_tasks())` 提交，`Scheduler.restore_pending_tasks()`（v0.0.5 已实现）执行：
1. 查询 `task_items` 中 `status IN ('pending', 'downloading', 'paused')` 的记录
2. 将 `downloading` 重置为 `paused`
3. 加入待下载队列

#### 3.8 task_completed 检测逻辑

`_check_task_completed(task_item_id)`:
1. 从 `task_item_repository.get_by_id(task_item_id)` 取 `TaskItem.task_id`
2. 从 `task_item_repository.get_by_task_id(task_id)` 取该 task 下所有子项
3. 若所有子项 `status == 'completed'` → `worker_signals.task_completed.emit(task_id)`
4. 若存在非 completed 子项（downloading/paused/pending/failed）→ 不触发

#### 4.5 链接解析流程（`_do_parse`）

```
_do_parse(text):
  try:
    links = text.strip().splitlines()  # 每行一个链接
    links = [l.strip() for l in links if l.strip()]
    total = len(links)
    results = []
    for i, line in enumerate(links, start=1):
      parsed = await url_parser.parse(line)   # URLParser.parse 为同步方法时用 run_in_thread 包装
      results.append(parsed)
      worker_signals.parse_progress.emit(i, total)
    worker_signals.parse_completed.emit(results)
  except asyncio.CancelledError:
    # 取消时不发 failed 信号，直接返回
    raise
  except Exception as e:
    worker_signals.parse_failed.emit(str(e))
```

**注**：`URLParser.parse` 在 v0.0.3 中为同步方法（含 httpx 重定向）。本里程碑在 asyncio loop 中调用时，需通过 `asyncio.to_thread(url_parser.parse, line)` 或 `async_worker.run_in_thread` 包装为协程，避免阻塞 loop。具体包装方式在实施时根据 v0.0.3 实际签名确定（若 v0.0.3 已提供 async 版本则直接 await）。

#### 4.6 主页抓取流程（`_do_home_fetch`）

```
_do_home_fetch(sec_user_id, filters):
  try:
    cookie_record = cookie_repository.get_valid()   # 取一条 valid Cookie
    cookie_content = cookie_record.content
    posts = []
    async for post in user_home_crawler.fetch_user_posts(
        sec_user_id, filters, cookie_content,
        progress_callback=self._on_home_fetch_progress):
      posts.append(post)
    worker_signals.home_fetch_completed.emit(posts)
  except asyncio.CancelledError:
    raise
  except CookieInvalidError as e:
    worker_signals.home_fetch_failed.emit("Cookie 失效，请更新")
  except Exception as e:
    worker_signals.home_fetch_failed.emit(str(e))
```

**注**：`UserHomeCrawler.fetch_user_posts` 在 v0.0.4 中返回 `AsyncIterator[PostItem]`，需用 `async for` 迭代。`progress_callback` 是同步回调，在迭代过程中被调用。

#### 4.7 取消机制

| 取消信号 | 持有的 Task 引用 | 取消方式 |
|---|---|---|
| `cancel_parse` | `_parse_task: asyncio.Task \| None` | `_parse_task.cancel()`，触发 `CancelledError` 在 `_do_parse` 中抛出 |
| `cancel_home_fetch` | `_home_fetch_task: asyncio.Task \| None` | `_home_fetch_task.cancel()`，触发 `CancelledError` 在 `_do_home_fetch` 中抛出，`async for` 迭代中断 |

- 取消时不发射 `parse_failed` / `home_fetch_failed` 信号（用户主动取消不算失败）。
- `CancelledError` 在 `_do_parse` / `_do_home_fetch` 中捕获后 `raise` 重新抛出，让 asyncio 正常清理。
- 若收到新的 `start_parse` 时已有任务在跑，先取消旧任务再启动新任务。

### 4.1 `worker/async_worker.py`

```python
from __future__ import annotations
import asyncio
import concurrent.futures
import threading
from collections.abc import Awaitable, Coroutine
from PySide6.QtCore import QObject, QThread


class AsyncWorker(QThread):
    """后台工作线程，承载 asyncio 事件循环。

    UI 线程通过 submit() 把协程调度到工作线程的 loop 中执行；
    工作线程内部通过 run_in_thread() 提交协程。
    stop() 时取消所有未完成任务并优雅退出。
    """

    def __init__(self, parent: QObject | None = None) -> None: ...

    def run(self) -> None:
        """QThread.run 重写：在工作线程创建并运行 asyncio loop。"""
        ...

    def start(self) -> None:
        """启动线程并等待 loop 就绪（超时 5 秒抛 RuntimeError）。"""
        ...

    def stop(self) -> None:
        """优雅关闭：设置停止信号，取消未完成任务，等待线程退出。"""
        ...

    def submit(self, coro: Coroutine) -> concurrent.futures.Future:
        """UI 线程提交协程到工作线程的 loop 执行。

        返回 concurrent.futures.Future，可在 UI 线程同步等待结果或添加回调。
        """
        ...

    def run_in_thread(self, coro: Coroutine) -> Awaitable:
        """工作线程内部提交协程（断言当前线程为工作线程）。

        返回 asyncio.Task（Awaitable），可在工作线程内 await。
        """
        ...

    async def _cleanup(self) -> None:
        """loop 退出前清理：取消所有未完成任务，停止 loop。"""
        ...
```

### 4.2 `worker/signals.py`

from __future__ import annotations
from PySide6.QtCore import QObject, Signal


class WorkerSignals(QObject):
    """工作线程 → UI 方向信号（由桥接器 emit，UI 槽接收）。"""

    # 下载相关
    progress_updated = Signal(list)        # list[ProgressUpdate]，批量进度（每 500ms）
    item_completed = Signal(int)           # task_item_id
    item_failed = Signal(int, str)         # task_item_id, fail_reason
    cookie_invalid = Signal(str)           # message（Cookie 全部失效提示）
    task_completed = Signal(int)           # task_id（某任务全部子项完成）

    # 解析相关
    parse_progress = Signal(int, int)      # current, total
    parse_completed = Signal(list)         # list[ParsedURL]
    parse_failed = Signal(str)             # reason

    # Cookie 测试
    cookie_test_result = Signal(int, bool, str)  # cookie_id, is_valid, message

    # 主页抓取
    home_fetch_progress = Signal(int, int)  # current, total（total 未知时为 0）
    home_fetch_completed = Signal(list)     # list[PostItem]
    home_fetch_failed = Signal(str)         # reason


class ControlSignals(QObject):
    """UI → 工作线程方向信号（由 UI emit，桥接器槽接收）。"""

    resume_all = Signal()

    start_parse = Signal(str)        # text（用户粘贴的链接文本）
    cancel_parse = Signal()

    # 主页抓取控制
    start_home_fetch = Signal(str, dict)  # sec_user_id, filters

## 7. 风险

### 7.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| QThread + asyncio loop 集成在 Windows 上行为异常（loop 启动失败、线程退出卡死） | 中 | 高 | 用 `threading.Event` 确保 loop 就绪后再返回 `start()`；`stop()` 设置超时强制 terminate；测试覆盖 Windows 平台 |
| `asyncio.run_coroutine_threadsafe` 返回的 Future 与内部 Task 跟踪困难 | 中 | 中 | `submit` 内部通过 `run_coroutine_threadsafe` 返回的 Future 的 `cb` 回调间接获取 Task 引用；或在 loop 内用 `ensure_future` 包装后再返回 |
| Qt 跨线程信号在测试中投递时机不确定（信号未及时处理就断言） | 中 | 中 | 测试中用 `qapp.processEvents()` 或 `QTimer.singleShot` 处理事件循环；用 `pytest-qt` 的 `qtbot.waitSignal` 等待信号 |
| `URLParser.parse` 为同步方法，在 asyncio loop 中直接调用会阻塞 loop | 中 | 中 | 用 `asyncio.to_thread()` 包装同步调用；或与 v0.0.3 协商提供 async 版本 |
| v0.0.5 的 Scheduler 未暴露 `on_all_cookies_invalid` 回调入口 | 中 | 中 | 本里程碑在 `_connect_scheduler_callbacks` 中预留连接逻辑；实施时核对 v0.0.5 实际接口，必要时协商 v0.0.5 补充回调参数 |
| 取消信号与任务完成的竞态（cancel 时任务刚好完成） | 低 | 低 | cancel 前检查 task.done()；已完成则不 cancel |
| `ProgressReporter` 的 `on_progress` 回调设置时机（Scheduler 内部创建 ProgressReporter，桥接器如何注入回调） | 中 | 中 | 实施时核对 v0.0.5 Scheduler 是否支持外部传入 `on_progress` 回调；若不支持，协商 Scheduler 增加 `set_progress_callback` 方法 |

### 7.2 依赖风险

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| v0.0.5 的 Scheduler 接口与计划文档有偏差（如回调签名、方法名） | 中 | 高 | 本里程碑启动前先核对 `downloader/scheduler.py` 实际实现与 v0.0.5 计划文档一致性；发现差异优先协商修改 v0.0.5 或适配 |

| v0.0.3 的 URLParser.parse 为同步方法，本里程碑假设需包装 | 中 | 低 | 实施时核对 v0.0.3 实际签名，若已是 async 则直接 await |

### 8.2 待 v0.0.7 确认的接口契约

- **WorkerSignals 的 list 类型信号元素类型**：`progress_updated` 的 list 元素是 `ProgressUpdate`，`parse_completed` 是 `ParsedURL`，`home_fetch_completed` 是 `PostItem`，`start_download` 是 `int`。v0.0.7 的 UI 槽函数需按此类型解构。
- **filters dict 结构**：`start_home_fetch` 的 filters dict key 为 `type_filter` / `max_count` / `start_date` / `end_date`，v0.0.7 的主页抓取过滤栏需按此结构构造 dict。
- **cookie_invalid 信号触发后的 UI 行为**：v0.0.7 收到 `cookie_invalid` 信号后应弹窗提示并跳转 Cookie 配置页（设计文档 7.2 节）。
- **task_completed 信号触发后的 UI 行为**：v0.0.7 收到后可更新任务行状态或显示完成提示。

### 8.3 遗留项（不在本里程碑处理）

- **main.py 装配**：创建 `AsyncWorker`、`Scheduler`、`DownloadBridge`、`CrawlerBridge`、`WorkerSignals`、`ControlSignals` 实例并注入依赖，属 v0.0.7。
- **UI 控件与信号连接**：UI 页面的按钮 clicked 信号 → `ControlSignals.emit`，`WorkerSignals` → UI 槽函数更新界面，属 v0.0.7。
- **Cookie 全池失效的 Scheduler 回调入口**：若 v0.0.5 未提供，需在 v0.0.7 装配时通过 HttpClient 回调间接连接，或协商 v0.0.5 补充。
- **真实抖音 API 联调**：本里程碑全部用 mock，真实联调留待 v0.0.7 UI 完成后整体集成测试。
