## 2. 架构概述

### 2.1 设计目标

本项目面向**非技术用户公开发布**，架构设计的首要目标是在「功能完备」与「交付简单」之间取得平衡：

| 设计目标 | 内涵 | 架构体现 |
|---|---|---|
| **单进程** | 全应用仅一个进程承载 UI、爬虫、下载引擎 | PySide6 + asyncio 同进程共存，避免 IPC 故障点 |
| **轻量** | 安装包小、启动快、资源占用低 | 仅依赖 PySide6 + httpx，安装包目标 60–80MB |
| **非技术用户友好** | 双击安装即用，零配置门槛 | 首次引导、图文教程、错误人话化、目录分离（卸载不丢数据） |
| **自主可控** | 核心爬虫组件不依赖第三方项目源码 | 签名算法、解析逻辑完全自主实现，外部依赖仅保留宽松协议通用库 |
| **可维护** | 抖音接口变更时定位明确、改动范围小 | 签名算法独立成模块，失效时只改一处 |
| **健壮** | 下载过程可中断、可恢复 | 任务队列续传 + 单文件分块续传 + 失败自动重试 |

### 2.2 技术选型及理由

#### 2.2.1 选型清单

| 层面 | 选型 | 版本下限 | 协议 | 选型理由 |
|---|---|---|---|---|
| UI 框架 | PySide6 (Qt) | 6.6 | LGPL | 安装包小、单进程、性能好，QSS 可做现代简洁界面；LGPL 协议可商用 |
| 爬虫语言 | Python | 3.10+ | PSF | 与签名算法实现一致，httpx 异步支持好 |
| HTTP 客户端 | httpx[http2] | 0.27 | BSD | 异步、支持 HTTP/2、支持 Range 分块续传，API 与 requests 兼容 |
| 数据库 | SQLite (WAL) | 内置 | 公有领域 | 轻量、无需安装、Python 标准库 sqlite3 直连，足够支撑任务持久化 |
| 打包 | PyInstaller --onedir | 6.x | GPL（输出非衍生） | onedir 启动快于 onefile，无解压临时目录 |
| 安装包 | Inno Setup | 6 | 免费使用 | Windows 生态成熟，支持自定义安装路径、注册表写入、卸载干净 |
| 测试 | pytest + vcrpy + respx | — | MIT/BSD | 异步测试、HTTP 录制回放、mock httpx 响应 |

#### 2.2.2 不选 Electron / Tauri 的理由

| 维度 | Electron | Tauri | 本项目（PySide6） |
|---|---|---|---|
| 参考项目语言 | 需用 JS/TS 重写签名算法 | 需用 Rust/JS 桥接 | 直接复用 Python 签名实现 |
| 安装包体积 | 150–200MB（含 Chromium + Node） | 30–80MB（前端资源另算） | 60–80MB |
| 进程模型 | 多进程（主+渲染+GPU） | 多进程（核心+WebView） | **单进程** |
| IPC 故障点 | 多 | 中 | 无 |
| 非技术用户友好 | 安装包大、启动慢 | WebView2 依赖系统环境 | 安装包小、启动快、依赖自包含 |

**结论**：参考项目为 Python，方案最大化复用既有签名实现，最小化体积，最少进程间通信故障点，最适合公开发布给非技术用户。

### 2.3 架构风格

本项目采用 **分层架构 + 信号驱动** 的混合风格：

- **分层架构**：自上而下分为 UI 层、工作线程层、下载引擎层、爬虫层、数据层。每层只依赖其直接下层，禁止反向依赖与跨层调用，确保职责清晰、可独立测试。
- **信号驱动**：UI 层与工作线程之间通过 Qt 信号/槽解耦。UI 不直接调用爬虫/下载引擎的阻塞方法，而是通过信号发起请求；工作线程通过信号回传进度与结果，实现 UI 不阻塞、交互即时响应。

这种组合在单进程桌面应用中是 Qt 生态的成熟范式，既能保持分层架构的可维护性，又能利用信号机制解决 UI 线程不能阻塞的硬约束。

### 3.2 分层职责边界

| 层 | 目录 | 职责 | 上游依赖 | 下游被依赖 |
|---|---|---|---|---|
| **UI 层** | `ui/` | 画界面、响应用户操作、发信号给工作线程、接收信号更新视图 | worker, models | 无（最上层） |
| **工作线程层** | `worker/` | 承载 asyncio 事件循环、桥接 Qt 信号与异步任务、协调爬虫与下载引擎调用 | downloader, crawlers, models | UI 层 |
| **下载引擎层** | `downloader/` | 任务调度、并发控制、httpx Range 分块下载、失败重试、进度汇报 | models | 工作线程层 |
| **爬虫层** | `crawlers/` | 链接解析、签名算法、视频解析、主页抓取、Cookie 池注入、HTTP 封装 | http_client（内部） | 工作线程层 |
| **数据层** | `app/` (database, models) | SQLite 连接管理、表初始化、迁移、数据模型定义、配置读写 | sqlite3（标准库） | 所有上层 |

### 3.3 依赖方向

**单向依赖规则**：依赖方向严格自上而下，禁止反向依赖与跨层调用。

```
UI 层  ──►  工作线程层  ──►  { 下载引擎层, 爬虫层 }  ──►  数据层
                                                  ▲
                                                  └── 爬虫层依赖自身 http_client
```

**约束细则**：

1. **下层不依赖上层**：`downloader/` 不得 import `ui/` 或 `worker/`；`crawlers/` 同理。
2. **不跨层调用**：UI 层不得直接调用 `downloader/` 或 `crawlers/`，必须经 `worker/` 桥接。
3. **数据层共享**：所有层可读 `models.py` 中的数据类定义（纯数据结构，无业务逻辑），但只有 `app/database.py` 持有 SQLite 连接与写入逻辑。
4. **信号反向通信合法**：工作线程通过 Qt 信号回传 UI 是例外，因为信号是 Qt 框架的线程安全机制，不构成 import 依赖。
5. **避免循环依赖**：跨层公共类型（异常、数据模型）统一收敛到 `app/models.py` 与 `crawlers/exceptions.py`，禁止在层间相互 import。

## 4. 线程模型设计

### 4.1 线程划分

本应用为单进程，但内部运行**两个关键线程**：

| 线程 | 类型 | 职责 | 不可阻塞 |
|---|---|---|---|
| **Qt 主线程** | UI 线程 | 跑 `QApplication.exec()`、事件循环、绘制界面、响应用户交互 | 是（阻塞即卡 UI） |
| **后台工作线程** | `QThread` 子类 | 跑 `asyncio` 事件循环，承载所有爬虫调用与下载任务 | 否（专门干重活） |

**为何不用多线程而用 asyncio**：

- 爬虫层与下载引擎均为 I/O 密集型（网络请求、磁盘写入），asyncio 协程切换成本远低于线程切换。
- 单 asyncio loop 内的协程天然共享同一上下文，无需 GIL 争抢，也无需复杂的线程同步原语。
- Qt 信号/槽已提供跨线程通信能力，无需再引入多线程同步复杂度。

### 4.2 线程通信机制

通信采用 **Qt 信号/槽**（`PySide6.QtCore.Signal` / `pyqtSignal`），由 Qt 框架保证线程安全：

- **工作线程 → UI 线程**：工作线程 emit 信号，Qt 自动将槽函数调用投递到 UI 线程的事件队列中执行（`Qt.QueuedConnection`）。
- **UI 线程 → 工作线程**：UI emit 信号，工作线程的槽函数在其 asyncio loop 线程中执行；槽内通过 `asyncio.run_coroutine_threadsafe()` 将操作投递到 loop 中执行。

**禁止的操作**：

- ❌ UI 线程直接调用工作线程的阻塞方法或 asyncio 协程
- ❌ 工作线程直接操作 UI 控件（必须通过信号回传）
- ❌ 跨线程共享可变状态而不加锁（应通过信号传值，而非共享引用）

### 4.3 信号清单

工作线程对外暴露的信号清单（定义在 `worker/async_worker.py` 的 `AsyncWorker(QThread)` 类中）：

#### 4.3.1 工作线程 → UI 线程（状态回传）

| 信号名 | 参数 | 触发时机 | UI 响应 |
|---|---|---|---|
| `progress_updated` | `(task_item_id: int, downloaded_bytes: int, total_bytes: int)` | 下载进度变化（500ms 节流） | 更新对应行的进度条与百分比 |
| `item_completed` | `(task_item_id: int, local_path: str)` | 单个任务项下载完成 | 行状态置为完成、进度条置 100%、绿色 |
| `item_failed` | `(task_item_id: int, reason: str)` | 单个任务项失败（重试耗尽） | 行状态置为失败、红色、显示失败原因 |
| `task_completed` | `(task_id: int)` | 整个任务所有项完成 | 任务级汇总更新、可选系统提示 |
| `parse_progress` | `(current: int, total: int, message: str)` | 链接解析/主页抓取进度 | 抓取页 loading 进度更新 |
| `parse_finished` | `(items: list[dict])` | 解析完成，返回作品列表 | 抓取页展示勾选列表 |
| `cookie_test_result` | `(cookie_id: int, valid: bool, message: str)` | Cookie 测试完成 | Cookie 页状态指示灯更新 |
| `cookie_pool_exhausted` | `()` | 所有 Cookie 失效 | 弹窗提示、暂停所有任务、跳转 Cookie 页 |
| `error_occurred` | `(scope: str, message: str, detail: str)` | 全局错误（磁盘满等） | 弹窗提示 |
| `log_message` | `(level: str, message: str)` | 工作线程日志 | 写日志文件（不显示 UI） |

#### 4.3.2 UI 线程 → 工作线程（控制指令）

| 信号名 / 方法名 | 参数 | 触发时机 | 工作线程响应 |
|---|---|---|---|
| `start_download(task_id)` | `task_id: int` | 用户点"开始下载" | 调度器启动该任务下的 pending 项 |
| `pause_item(task_item_id)` | `task_item_id: int` | 用户点单项"暂停" | 取消该协程、状态置 paused、保留 .part |
| `resume_item(task_item_id)` | `task_item_id: int` | 用户点单项"恢复" | 重建协程、Range 续传 |
| `pause_all()` | — | 用户点"全部暂停" | 取消所有 downloading 协程 |
| `resume_all()` | — | 用户点"全部开始" | 重建所有 paused 协程 |
| `parse_urls(text, filters)` | `text: str, filters: dict` | 抓取页点"开始解析" | 调 URLParser + VideoParser/UserHomeCrawler |
| `test_cookie(cookie_id)` | `cookie_id: int` | Cookie 页点"测试" | 调轻量 API 验证 Cookie |
| `shutdown()` | — | 应用关闭 | 优雅停止 loop、持久化进度 |

### 4.4 线程安全注意事项

1. **SQLite 跨线程访问**：SQLite 默认禁止跨线程共用连接。本项目采用「**每线程一连接**」策略：
   - UI 线程只读查询（任务列表展示）使用 UI 线程连接
   - 工作线程的所有写入使用工作线程连接
   - 通过 `check_same_thread=False` + 应用层约束保证不混用
   - WAL 模式允许读写并发，避免读写互斥

2. **进度数据传递**：进度信号传递的是值类型（int、str），不存在共享可变引用问题。禁止在信号中传递 `dict` / `list` 后又在原线程修改它。

3. **任务取消的及时性**：`asyncio.Task.cancel()` 只在协程下一个 await 点抛出 `CancelledError`，长流式下载需在每块数据写入后检查 `CancelledError`，确保暂停及时生效（不超过 64KB 数据量的延迟）。

4. **关闭时序**：应用退出时按以下顺序：
   - UI 发 `shutdown` 信号 → 工作线程停止接收新任务
   - 等待在途协程完成或取消（最长 5s 超时）
   - 持久化所有 downloading 项为 paused、刷新 downloaded_bytes
   - 关闭 SQLite 连接 → 退出 asyncio loop → 退出 QThread

## 5. 并发控制设计

### 5.1 下载并发

- **机制**：`asyncio.Semaphore` 限制同时在飞的下载协程数。
- **默认值**：3（在设置页可配，范围 1–10）。
- **上限**：10（超过 10 易触发抖音风控，硬编码上限）。
- **配置存储**：`config` 表 `key='max_concurrency'`，应用启动时读取并创建 Semaphore。
- **运行时调整**：用户修改并发数后，需重建 Semaphore（已有协程不中断，新协程按新值排队）。简单实现：仅在下次启动下载任务时生效，运行中调整提示"下次任务生效"。

```
Scheduler 调度流程：
  for item in pending_items:
      async with semaphore:           # 并发数受 Semaphore 约束
          await downloader.download(item)
```

### 5.2 图集子并发

图集类型（`image_set`）一个作品含多张图片，需在单项下载器内部再开子并发：

- **机制**：`Downloader.download()` 内部为每张图片创建协程，用一个独立的「子 Semaphore」限制图集内部并发。
- **约束**：子 Semaphore 容量 ≤ 总 Semaphore 剩余容量，避免图集单项独占全部并发。
- **推荐配置**：图集子并发 = `min(5, max_concurrency)`，硬编码上限 5。
- **总并发关系**：图集占 1 个外层 Semaphore 配额，内部最多 5 张图片并行下载，确保不挤占其他任务过多配额。

```
Downloader.download(item) 流程（图集）：
  async with outer_semaphore:            # 占 1 个总配额
      sub_sem = asyncio.Semaphore(min(5, max_concurrency))
      await asyncio.gather(*[
          sub_sem.acquire() then download_image(url)
          for url in item.image_urls
      ])
```

### 5.3 进度信号节流

**问题**：流式下载每 64KB 产生一次进度更新，10 个并发任务 × 频率 = 每秒数百次信号，UI 线程事件队列会被淹没，导致界面卡顿。

**方案**：`asyncio.Queue` + 专门的「进度汇报协程」批量节流：

```
┌─────────────── 下载引擎 ─────────────────┐
│  各下载协程  ──put──►  asyncio.Queue      │
│                         (最新值覆盖旧值)   │
│                                              │
│  ProgressReporter 协程:                    │
│    每 500ms 从 Queue 取出所有最新值         │
│    合并成一批 → emit 一次 progress_updated  │
│    (每项只发最新值，丢弃中间值)             │
└──────────────────────────────────────────┘
              │ 信号 (线程安全)
              ▼
        UI 线程批量刷新可见行
```

**实现要点**：

- Queue 中以 `task_item_id` 为 key 去重，汇报时只取每个 id 的最新值（旧值丢弃，避免无意义中间刷新）。
- 节流周期 500ms 是经验值：人眼对进度条刷新频率的感知阈值约 2Hz，500ms（2Hz）足够流畅且不卡 UI。
- UI 侧只刷新可见行（`QListView` 模型按需刷新），不可见行不重绘。
- 完成与失败信号不节流，立即发送（量小且需要即时反馈）。

## 6. 核心组件设计

### 6.1 爬虫组件层

爬虫组件层位于 `crawlers/`，是本项目自主实现的核心模块，不依赖任何第三方爬虫项目源码。

#### 6.1.1 URLParser（链接解析器）

- **职责**：从用户粘贴的文本中提取抖音链接、识别类型（视频/图集/长视频/用户主页），返回结构化结果。
- **输入**：用户粘贴的原始文本（可能含分享口令、短链、长链、多行混合）。
- **输出**：解析结果列表，每项含 `{type, url, aweme_id | sec_user_id}`。
- **实现要点**：正则提取 URL → httpx 跟随重定向拿到最终 URL → 解析查询参数判定类型。

**接口签名**：

```python
class URLParser:
    def __init__(self, http_client: HttpClient) -> None: ...

    async def parse(self, text: str) -> list[ParsedURL]:
        """
        解析用户粘贴文本，返回所有识别到的链接信息。
        ParsedURL 字段：
          type: Literal['video', 'image_set', 'long_video', 'user_home']
          url: str                  # 规范化后的最终 URL
          aweme_id: str | None      # 视频类有值
          sec_user_id: str | None   # 用户主页有值
        """

    async def parse_single(self, text: str) -> ParsedURL:
        """解析单条文本，失败抛 URLParseError。"""
```

**识别规则**：

| 文本特征 | 判定类型 |
|---|---|
| 含 `aweme_id` 参数 | 视频 / 图集 / 长视频（具体类型解析后才知道） |
| 含 `sec_user_id` 或路径 `/user/` | 用户主页 |
| 抖音短链 `v.douyin.com/xxx` | 先重定向再按上述规则判断 |
| 分享口令「…复制此链接…」 | 提取其中的 URL 后按上述规则判断 |

#### 6.1.2 Signer（签名算法模块）—— 最核心、最易失效

- **职责**：为请求 URL 生成 `X-Bogus` / `A_Bogus` / `msToken` / `verify_fp` 等签名参数，使请求通过抖音服务端校验。
- **实现要点**：参考 A-Bogus 算法的公开原理，用 Python 自主实现，不调用任何外部 JS 引擎或 Node 服务。
- **子模块**：
  - `xbogus.py` — X-Bogus 签名
  - `abogus.py` — A_Bogus 签名
  - `mstoken.py` — msToken 生成
  - `verify_fp.py` — verify_fp / s_v_web_id 生成
- **维护策略**：算法失效时只改这一个模块，不影响其他组件（见 9.3）。

**接口签名**：

```python
class Signer:
    def sign(self, url: str, params: dict[str, Any]) -> dict[str, str]:
        """
        为请求生成签名参数，返回需追加到 query 的参数字典。
        返回示例：{'X-Bogus': '...', 'A_Bogus': '...', 'msToken': '...', '_signature': '...'}
        """

    def generate_mstoken(self) -> str:
        """生成 msToken（部分接口仅需 msToken）。"""

    def generate_verify_fp(self) -> str:
        """生成 verify_fp / s_v_web_id（首次会话生成一次，复用）。"""
```

#### 6.1.3 VideoParser（视频解析器）

- **职责**：根据 `aweme_id` 调用抖音详情接口，提取无水印直链与元数据。
- **输入**：`aweme_id` + Cookie。
- **调用接口**：`aweme/v1/web/aweme/detail`（经签名）。
- **输出**：`{type, title, author, duration, cover_url, no_watermark_url, image_urls[]}`。
- **无水印提取逻辑**：

  - 图集：从 `images[].url_list` 取原图直链

**接口签名**：

```python
class VideoParser:
```

#### 6.1.4 UserHomeCrawler（主页抓取器）

- **职责**：根据 `sec_user_id` 分页拉取用户主页作品列表，按过滤条件筛选后返回。
- **输入**：`sec_user_id` + Cookie + 过滤条件（类型 / 数量上限 / 时间段）。
- **调用接口**：`aweme/v1/web/aweme/post` 分页拉取。
- **分页逻辑**：维护 `max_cursor`，每页约 20 条，循环拉取直到无更多或达到上限。
- **过滤逻辑**：在内存中按 `create_time`（时间段）和 `aweme_type`（视频/图文）过滤。
- **输出**：作品列表 `[{aweme_id, title, cover_url, type, ...}]`，交 UI 供用户勾选。

**接口签名**：

```python
class UserHomeCrawler:
    def __init__(self, http_client: HttpClient, signer: Signer) -> None: ...

    async def fetch(
        self,
        sec_user_id: str,
        filters: HomeFilters,

        """
        分页拉取用户主页作品并按条件过滤。
        HomeFilters 字段：
          type_filter: Literal['all', 'video', 'image_set', 'long_video']

          start_date: str | None          # ISO8601 日期
          end_date: str | None
        HomeItem 字段：
          aweme_id, title, cover_url, type, duration, image_count, author, create_time
```

#### 6.1.5 HttpClient（HTTP 客户端）

- **职责**：封装 `httpx.AsyncClient` 单例，统一注入 Cookie、User-Agent、Referer、签名参数，分类错误。
- **超时配置**：连接 10s，读取 30s。
- **Cookie 池注入**：每次请求从 Cookie 池取 `status='valid'` 且 `last_used` 最早的（最久未用优先，均衡负载）。
- **错误分类**：网络异常 / HTTP 状态码 / 风控响应，分别抛对应异常。

**接口签名**：

```python
class HttpClient:
    def __init__(self, cookie_pool: CookiePool) -> None: ...

    async def request(
        self,
        method: str,
        url: str,
        *,
        params: dict[str, Any] | None = None,
        headers: dict[str, str] | None = None,
        sign: bool = True,
    ) -> httpx.Response:
        """
        发起请求，自动注入 Cookie、签名、统一 Headers。
        sign=True 时调用 Signer 对 params 签名后追加。
        失败时抛：NetworkError / CookieInvalidError / RateLimitedError
        """

    async def stream_download(
        self,
        url: str,
        *,
        start_byte: int = 0,
        headers: dict[str, str] | None = None,
    ) -> AsyncIterator[bytes]:
        """
        流式下载，支持 Range 分块续传。
        start_byte > 0 时自动添加 Range: bytes={start_byte}- 头。
        yields: bytes 数据块
        """
```

#### 6.1.6 异常体系

爬虫层自定义异常位于 `crawlers/exceptions.py`，下载引擎与 UI 层据此决定行为：

| 异常类型 | 触发场景 | 处理方式 |
|---|---|---|
| `CookieInvalidError` | 请求返回 461/412，Cookie 失效或被限流 | 跳转 Cookie 配置页 |
| `RateLimitedError` | 触发风控限流 | 该项标记失败，原因提示等待 |
| `VideoNotFoundError` | 作品已删除/私密 | 标记该项失败，原因写明 |
| `NetworkError` | 连接超时/DNS 失败 | 交下载引擎重试逻辑 |
| `URLParseError` | 链接格式无法识别 | UI 输入框下方红字提示 |
| `SignError` | 签名算法异常 | 标记失败，记录日志供排查 |

### 6.2 下载引擎

下载引擎位于 `downloader/`，负责并发下载、分块续传、失败重试、进度汇报。只负责文件下载，不负责链接解析。

#### 6.2.1 Scheduler（任务调度器）

- **职责**：维护待下载队列、控制并发、处理暂停/恢复、协调单项下载器。
- **输入**：从 SQLite 取 `task_items`（status=pending/downloading/paused）。
- **输出**：通过 `ProgressReporter` 发信号回 UI。

**接口签名**：

```python
class Scheduler:
    def __init__(
        self,
        downloader: Downloader,
        reporter: ProgressReporter,
        max_concurrency: int = 3,
    ) -> None: ...

    async def start_task(self, task_id: int) -> None:
        """启动一个任务下所有 pending/paused 项的下载。"""

    async def pause_item(self, task_item_id: int) -> None:
        """暂停单个项：取消协程、状态置 paused、保留 .part。"""

    async def resume_item(self, task_item_id: int) -> None:
        """恢复单项：重建协程、Range 续传。"""

    async def pause_all(self) -> None: ...
    async def resume_all(self) -> None: ...

    async def shutdown(self) -> None:
        """优雅关闭：持久化所有 downloading 为 paused。"""
```

#### 6.2.2 Downloader（单项下载器）

- **职责**：下载单个任务项（视频/图集/长视频），httpx Range 分块、写 .part 文件、失败重试。
- **重试策略**：网络异常 / HTTP 5xx / 风控限流（461/412）触发重试；指数退避 2s/4s/8s；3 次后置 failed。HTTP 4xx（非限流）直接失败不重试。
- **持久化节奏**：每 5s 或每 1MB 持久化一次 `downloaded_bytes` 到 SQLite，防止崩溃丢失进度。

**接口签名**：

```python
class Downloader:
    def __init__(self, http_client: HttpClient, reporter: ProgressReporter) -> None: ...

    async def download(self, item: TaskItem, download_dir: Path) -> None:
        """
        下载单个任务项。
        - 视频/长视频：单文件 Range 续传，写 .part，完成改名
        - 图集：内部开子并发下载多张图片，每张走 .part 流程
        - 失败重试 ≤ 3 次，指数退避
        - 完成发 item_completed，失败发 item_failed
        """

    async def _download_single_file(
        self, url: str, dest: Path, start_byte: int, item_id: int
    ) -> None:
        """单文件分块续传内部方法。"""
```

#### 6.2.3 ProgressReporter（进度信号节流器）

- **职责**：接收各下载协程的进度更新，500ms 批量节流后发 `progress_updated` 信号。
- **机制**：内部维护 `asyncio.Queue` + 汇报协程。

**接口签名**：

```python
class ProgressReporter(QObject):
    # Qt 信号（在工作线程中 emit，UI 线程接收）
    progress_updated = Signal(int, int, int)   # task_item_id, downloaded, total
    item_completed = Signal(int, str)          # task_item_id, local_path
    item_failed = Signal(int, str)             # task_item_id, reason

    def __init__(self) -> None: ...

    def update(self, task_item_id: int, downloaded: int, total: int) -> None:
        """下载协程调用，将进度更新放入 Queue（非阻塞）。"""

    async def run(self) -> None:
        """汇报协程主循环：每 500ms 从 Queue 取最新值批量发信号。"""

    def emit_completed(self, task_item_id: int, local_path: str) -> None:
        """立即发送完成信号（不节流）。"""

    def emit_failed(self, task_item_id: int, reason: str) -> None:
        """立即发送失败信号（不节流）。"""
```

#### 6.2.4 组件协作关系

```
Scheduler ──acquire semaphore──► Downloader.download(item)
                                      │
                                      ├─ httpx Range 请求 ──► HttpClient.stream_download
                                      │
                                      ├─ 写 .part 文件
                                      │   └─ 每 5s/1MB 持久化 downloaded_bytes 到 SQLite
                                      │
                                      ├─ 每数据块 ──► ProgressReporter.update()  (put Queue)
                                      │
                                      ├─ 失败 ──► 重试 (≤3) / ProgressReporter.emit_failed()
                                      │
                                      └─ 完成 ──► .part 改名 ──► ProgressReporter.emit_completed()

ProgressReporter 汇报协程:
    每 500ms ──► 从 Queue 取最新值 ──► emit progress_updated 信号 ──► UI 线程
```

### 6.3 工作线程桥接（AsyncWorker）

工作线程层位于 `worker/`，核心是 `AsyncWorker(QThread)`，负责在 QThread 中跑 asyncio loop 并桥接 Qt 信号与异步任务。

#### 6.3.1 桥接方式

```
┌──────────── UI 线程 ────────────┐    ┌──────── 工作线程 (QThread) ────────┐
│                                  │    │                                     │
│  AsyncWorker.start()             │───►│  AsyncWorker.run():                 │
│    └─ QThread 启动               │    │    loop = asyncio.new_event_loop() │
│                                  │    │    asyncio.set_event_loop(loop)    │
│  UI 调用 worker.start_download() │    │    loop.run_forever()              │
│    └─ 通过 Signal 发送           │───►│    槽函数内：                       │
│                                  │    │    asyncio.run_coroutine_threadsafe│
│                                  │    │      (scheduler.start_task(id),   │
│                                  │    │       loop)                        │
│                                  │    │                                     │
│  UI 接收信号                     │◄───│  ProgressReporter.emit 信号        │
│    └─ Qt 自动投递到 UI 事件队列  │    │    (Qt 跨线程 QueuedConnection)    │
└──────────────────────────────────┘    └─────────────────────────────────────┘
```

**关键点**：

1. `AsyncWorker` 继承 `QThread`，重写 `run()` 在其中创建并运行 asyncio loop。
2. UI 线程通过 `asyncio.run_coroutine_threadsafe(coro, loop)` 将协程投递到工作线程的 loop 中执行。
3. 工作线程内的信号 emit 由 Qt 自动通过 `Qt.QueuedConnection` 投递到 UI 线程事件队列执行槽函数。
4. UI 线程永远不直接 `await` 协程，也不直接操作 loop。

#### 6.3.2 接口签名

```python
class AsyncWorker(QThread):
    # 向 UI 发送的信号（见 4.3.1 信号清单）
    progress_updated = Signal(int, int, int)
    item_completed = Signal(int, str)
    item_failed = Signal(int, str)
    task_completed = Signal(int)
    parse_progress = Signal(int, int, str)
    parse_finished = Signal(list)
    cookie_test_result = Signal(int, bool, str)
    cookie_pool_exhausted = Signal()
    error_occurred = Signal(str, str, str)
    log_message = Signal(str, str)

    def __init__(self) -> None: ...

    def run(self) -> None:
        """QThread 入口：创建 asyncio loop 并 run_forever。"""

    # UI 调用的方法（内部通过 run_coroutine_threadsafe 投递到 loop）
    def start_download(self, task_id: int) -> None: ...
    def pause_item(self, task_item_id: int) -> None: ...
    def resume_item(self, task_item_id: int) -> None: ...
    def pause_all(self) -> None: ...
    def resume_all(self) -> None: ...
    def parse_urls(self, text: str, filters: dict) -> None: ...
    def test_cookie(self, cookie_id: int) -> None: ...
    def shutdown(self) -> None: ...
```

## 8. 打包与部署设计

### 8.1 PyInstaller --onedir 打包方案

**选型理由**：`--onedir` 模式启动快于 `--onefile`（无需每次启动解压到临时目录），且便于增量更新依赖。

**打包命令**：

```
PyInstaller --onedir --windowed --name DouyinCatcher
            --icon assets/icon.ico
            --add-data "ui/assets;ui/assets"
            --add-data "assets;assets"
            main.py
```

**参数说明**：

| 参数 | 作用 |
|---|---|
| `--onedir` | 生成目录而非单 exe，启动快 |
| `--windowed` | 不弹控制台黑框（GUI 应用必备） |
| `--name DouyinCatcher` | 输出目录与 exe 名称 |
| `--icon assets/icon.ico` | 应用图标 |
| `--add-data "ui/assets;ui/assets"` | 打包 QSS 样式与教程截图（Windows 用 `;` 分隔） |
| `--add-data "assets;assets"` | 打包全局图标资源 |

**产物结构**：

```
dist/DouyinCatcher/
├── DouyinCatcher.exe              # 启动器（用户双击）
├── _internal/                      # 依赖与资源
│   ├── PySide6/
│   ├── httpx/
│   ├── ...
│   ├── ui/assets/                  # QSS + 教程截图
│   └── assets/                     # 图标
└── (其他 PyInstaller 自动生成的文件)
```

**体积控制**：

- 目标安装包 60–80MB（PySide6 + httpx + Python 运行时）
- 通过 PyInstaller 的 `excludes` 排除未使用的模块（如 tkinter、unittest）进一步瘦身

### 8.2 Inno Setup 安装包

**选型理由**：Inno Setup 是 Windows 生态成熟的免费安装包制作工具，支持自定义安装路径、注册表写入、开始菜单快捷方式、卸载干净。

**安装包设计**：

- **安装路径默认值**：`C:\Program Files\DouyinCatcher`（标准程序目录）
- **快捷方式**：开始菜单 + 桌面（可选）
- **注册表项**：写入卸载信息到 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\DouyinCatcher`
- **文件关联**：不关联任何文件类型
- **卸载行为**：只卸载程序目录，**不删除** `%APPDATA%/DouyinCatcher/` 用户数据
- **升级**：检测到旧版本时提示先卸载（简化升级流程，YAGNI 不做自动升级）

**产物**：`DouyinCatcher_Setup.exe`（约 30–40MB，压缩后）

### 8.3 运行时数据位置

运行时数据存放于 `%APPDATA%/DouyinCatcher/`（即 `C:\Users\<用户名>\AppData\Roaming\DouyinCatcher\`）：

```
%APPDATA%/DouyinCatcher/
├── data.db                         # SQLite 数据库（任务/任务项/元数据/Cookie池/配置）
└── logs/
    └── app.log                     # 应用日志（按天滚动，保留 7 天）
        app.log.2026-07-10
        app.log.2026-07-09
        ...
```

**选择 %APPDATA% 的理由**：

1. **Windows 标准**：Roaming 目录是 Windows 推荐的用户级应用数据存放位置。
2. **卸载不丢**：程序卸载只删 `Program Files\DouyinCatcher`，不影响 `%APPDATA%` 下数据。
3. **重装不丢**：用户重装系统前若备份 Roaming 目录，可完整恢复任务与配置。
4. **权限友好**：用户目录无需管理员权限写入，避免 UAC 弹窗。

### 8.4 程序目录与用户数据目录分离策略

| 内容 | 存放位置 | 卸载是否保留 |
|---|---|---|
| 可执行文件与依赖 | `C:\Program Files\DouyinCatcher\` | 删除 |
| 应用图标等资源 | 打包进 exe，运行时释放到内存 | — |
| SQLite 数据库 | `%APPDATA%\DouyinCatcher\data.db` | **保留** |
| 日志文件 | `%APPDATA%\DouyinCatcher\logs\` | **保留** |
| 下载的文件 | 用户在设置页指定的下载目录（默认 `%USERPROFILE%\Downloads\DouyinCatcher`） | **保留** |

**路径解析逻辑**（`app/config.py`）：

- `APP_DATA_DIR = os.path.expandvars(r'%APPDATA%\DouyinCatcher')`
- 首次启动时若该目录不存在则创建
- 数据库与日志路径均基于 `APP_DATA_DIR` 拼接

**升级与卸载影响**：

- 升级：只替换程序目录，用户数据零影响
- 卸载：用户数据保留，重装后无缝恢复任务队列与 Cookie 池
- 用户若需彻底清理，需手动删除 `%APPDATA%\DouyinCatcher\`（在 README 说明）

## 9. 关键技术决策记录

### 9.1 为何自主实现爬虫而非依赖开源项目

**背景**：开源项目 `Evil0ctal/Douyin_TikTok_Download_API` 已提供抖音抓取能力，是否直接 vendoring 或 import 其源码？

**决策**：**完全自主实现，不依赖其源码**，仅参考设计思路。

**理由**：

| 维度 | 依赖开源项目源码 | 自主实现 |
|---|---|---|
| 协议风险 | 需遵守其开源协议，可能传染 | 无传染风险，可任意发布 |
| 维护成本 | 跟随上游变更被动 | 主动可控，按需调整 |
| 体积 | 引入额外依赖 | 最小化依赖 |
| 安全 | 第三方代码审计成本高 | 自有代码可全程审计 |
| 学习与掌控 | 黑盒 | 团队掌握核心能力 |

**实施约束**：

- 不 vendoring 其源码，不 import 其模块
- 签名算法、解析逻辑参考其设计，完全自主实现为本项目自有组件
- 仓库 README 中注明设计参考来源

### 9.2 为何选择 SQLite 而非其他数据库

**决策**：**SQLite（WAL 模式）**，不选 MySQL/PostgreSQL/Redis/JSON 文件。

| 候选 | 否决理由 |
|---|---|
| MySQL / PostgreSQL | 需用户安装数据库服务，违背「非技术用户双击即用」目标 |
| Redis | 内存数据库，重启丢数据；需额外服务进程 |
| JSON 文件 | 无事务、无并发写支持、断点续传场景下数据易损坏 |
| **SQLite** | ✅ 单文件、零配置、Python 标准库直连、WAL 支持并发读写、性能足够 |

**SQLite 适用性论证**：

- **数据量级**：单用户任务量级为千条级，SQLite 单表百万行无压力
- **并发量级**：单进程两线程（UI + 工作线程），WAL 模式支持读写并发，无锁竞争
- **持久化需求**：断点续传要求 ACID，SQLite 事务保证
- **部署成本**：零，Python 标准库内置 `sqlite3` 模块

**WAL 模式开启**：`PRAGMA journal_mode=WAL`，在 `app/database.py` 初始化时执行。

### 9.3 签名算法的持续维护策略

**问题**：抖音签名算法（X-Bogus / A_Bogus / msToken）是本项目最易失效的部分，抖音服务端升级可能导致签名算法失效。如何设计才能在失效时快速修复？

**决策**：**签名算法独立成 `crawlers/signer/` 模块，与业务逻辑解耦，提供稳定接口，失效时只改此模块。**

**维护策略**：

1. **接口稳定**：`Signer.sign(url, params) -> dict` 接口固定，内部算法变更不影响调用方。
2. **子模块隔离**：X-Bogus / A_Bogus / msToken / verify_fp 各自独立文件，某个算法失效只改对应文件。
3. **测试用例驱动**：维护已知输入/输出对的测试用例（依据公开原理和本项目实现独立生成、核验），算法变更必须附带新用例。
4. **VCR 录制回放**：爬虫层测试用 VCR.py 录制真实响应，算法失效时测试先红，定位明确。
5. **运行时降级**：签名失败时抛 `SignError`，该项标记失败但不崩溃，其他任务不受影响。
6. **快速热修通道**：签名模块是纯 Python 无外部依赖，修复后只需重新打包发布，用户升级即可恢复。

**失效应急流程**：

```
用户反馈"无法下载"
    │
    ▼
开发者本地用实时 Cookie 验证签名算法
    │
    ├─ 算法失效 ──► 定位到具体子模块 ──► 修改 ──► 跑测试用例 ──► 发版
    │
    └─ Cookie 失效 ──► 引导用户更新 Cookie（非代码问题）
```

## 10. 架构风险与缓解措施

### 10.1 签名算法失效风险

| 维度 | 说明 |
|---|---|
| **风险描述** | 抖音升级签名算法（X-Bogus / A_Bogus），本项目自有实现无法通过服务端校验，导致所有解析请求失败 |
| **发生概率** | 中（抖音历史上每数月变更一次） |
| **影响范围** | 高（全应用核心功能不可用） |
| **缓解措施** | 1. 签名算法独立成模块，接口稳定，失效时只改一处<br>2. 维护已知输入/输出对测试用例，CI 阻断退化<br>3. VCR 录制真实响应，算法失效时测试先红<br>4. 运行时签名失败抛 `SignError` 不崩溃，其他模块不受影响<br>5. 建立快速热修与发版通道，纯 Python 修改无需重构 |
| **应急方案** | 用户反馈后，开发者本地用实时 Cookie 复现 → 修改签名子模块 → 发版升级 |

### 10.2 抖音风控风险

| 维度 | 说明 |
|---|---|
| **风险描述** | 高频请求或异常 User-Agent 触发抖音风控，返回 461/412 或滑动验证 HTML，导致下载中断 |
| **发生概率** | 中高（批量下载场景下几乎必然遇到） |
| **影响范围** | 中（单项失败，不影响其他项） |
| **缓解措施** | 1. 并发上限硬编码 10，默认 3，避免过高并发<br>2. Cookie 池轮换 + 健康检查，单 Cookie 失效自动切换<br>3. 失败重试指数退避（2s/4s/8s），避免短时间内重复触发风控<br>4. 风控响应明确分类（461/412 → Cookie 失效；验证 HTML → 触发验证），给用户清晰提示<br>5. 不实现自动过验证（合规与稳定考量），遇验证即标记失败<br>6. 统一 User-Agent 与 Referer，模拟正常浏览器请求 |
| **应急方案** | 用户更新 Cookie + 降低并发数 + 稍后重试 |

### 10.3 Cookie 失效风险

| 维度 | 说明 |
|---|---|
| **风险描述** | 抖音 Cookie 有效期有限（通常数天到数周），失效后所有请求返回 461/412 |
| **发生概率** | 高（必然发生，时间问题） |
| **影响范围** | 高（全应用核心功能不可用） |
| **缓解措施** | 1. Cookie 池支持多 Cookie 轮换，单条失效不中断下载<br>2. 每次请求选最久未用的 valid Cookie，均衡负载延长整体寿命<br>3. 连续失败 3 次自动置 invalid，切换下一条<br>4. 池里所有 Cookie 失效时暂停所有任务 + 弹窗提示 + 跳转 Cookie 配置页<br>5. Cookie 配置页提供「测试 Cookie」按钮，用户主动验证有效性<br>6. Cookie 教程图文引导，降低非技术用户更新门槛 |
| **应急方案** | 用户按教程重新获取 Cookie → 添加到池 → 测试通过 → 恢复下载 |

### 10.4 其他风险

| 风险 | 缓解措施 |
|---|---|
| **SQLite 损坏** | WAL 模式提升可靠性；定期 `PRAGMA integrity_check`；建议用户偶尔导出备份（YAGNI，暂不实现自动备份） |
| **磁盘空间不足** | 写 .part 文件时捕获 OSError，弹窗提示更换目录或清理磁盘 |
| **大文件下载中断** | 每 5s 或每 1MB 持久化 downloaded_bytes，崩溃重启后 Range 续传，损失 ≤ 1MB |
| **PyInstaller 打包兼容性** | CI 中验证打包能否成功；锁定 PySide6/httpx 版本下限，避免依赖破坏性升级 |
| **HTTP/2 连接复用问题** | httpx.AsyncClient 单例，连接池复用；遇到连接异常自动重试 |
