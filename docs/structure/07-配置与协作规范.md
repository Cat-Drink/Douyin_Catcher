## 2. 项目环境配置

### 2.1 开发环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| Python | 3.11+ | 必须使用 3.11 或更高版本（依赖 httpx[http2]、PySide6 6.6+ 的最低要求） |
| 操作系统 | Windows 10 / Windows 11 | 开发可跨平台（macOS/Linux 可运行测试），但**打包与发布仅支持 Windows** |
| Git | 2.30+ | 版本控制工具 |
| pip | 23.0+ | Python 包管理器（随 Python 一同安装） |
| venv | 内置 | Python 虚拟环境（随 Python 一同安装） |
| 磁盘空间 | ≥ 2GB | 包含依赖、虚拟环境、构建产物 |
| 内存 | ≥ 4GB | 推荐 8GB+（PySide6 + PyInstaller 打包较占内存） |

**可选工具**：
- [Inno Setup](https://jrsoftware.org/isinfo.php) 6.0+：用于生成 Windows 安装包
- [gitleaks](https://github.com/gitleaks/gitleaks)：用于本地检测 Cookie/密钥泄漏
- VSCode：推荐的集成开发环境（见 2.3）

### 2.2 项目初始化步骤

#### 2.2.1 克隆仓库

```bash
git clone <仓库地址> Douyin_Catcher
cd Douyin_Catcher
```

#### 2.2.2 创建虚拟环境

**Windows (PowerShell)**：
```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

**Windows (cmd)**：
```cmd
python -m venv .venv
.\.venv\Scripts\activate.bat
```

**macOS / Linux**：
```bash
python3 -m venv .venv
source .venv/bin/activate
```

#### 2.2.3 安装运行依赖

```bash
pip install -r requirements.txt
```

`requirements.txt` 内容见 3.1 节。

#### 2.2.4 安装开发依赖

```bash
pip install -r requirements-dev.txt
```

`requirements-dev.txt` 内容见 3.2 节。

#### 2.2.5 初始化数据库

应用首次启动时由 `app/database.py` 自动完成表结构创建与 WAL 模式开启，无需手动操作。

如需手动初始化（用于测试环境）：
```bash
python -c "from app.database import init_db; init_db()"
```

#### 2.2.6 配置测试 Cookie（仅测试需要）

复制 `.env.example` 为 `.env`，填入测试 Cookie（见 2.4 节）。

#### 2.2.7 验证环境

```bash
# 验证依赖安装
python -c "import PySide6; import httpx; print('依赖 OK')"

# 运行测试套件
pytest

# 启动应用（仅 Windows 可见 UI）
python main.py
```

### 2.4 环境变量

#### 2.4.1 `.env` 文件用途

- **唯一用途**：存放测试所需的抖音 Cookie（仅本地测试与 VCR.py 录制使用）
- **不入库**：`.env` 已加入 `.gitignore`，严禁提交
- **不打包**：PyInstaller 打包配置中显式排除 `.env`
- **CI 环境**：CI 不读取 `.env`，所有测试用 VCR.py 录制回放

#### 2.4.2 `.env.example` 模板

```env

# ========================================

# 警告：测试完成后请清除 .env 中的 Cookie 内容

# 抖音测试 Cookie（从浏览器开发者工具复制，仅用于本地测试）
# 获取方式见设计文档 7.5 节 Cookie 教程
DOUYIN_TEST_COOKIE=

# 测试用用户主页 sec_user_id（可选，用于主页抓取测试）
```

## 3. 依赖管理规范

### 3.1 运行依赖清单

`requirements.txt`：
```
PySide6>=6.6
httpx[http2]>=0.27
```

| 依赖 | 版本 | 协议 | 用途 |
|---|---|---|---|
| PySide6 | >=6.6 | LGPL | Qt GUI 框架（UI 层） |
| httpx[http2] | >=0.27 | BSD-3-Clause | 异步 HTTP 客户端（爬虫层、下载引擎） |

**依赖选型原则**：
- 仅引入宽松协议（LGPL / BSD / MIT / Apache 2.0）的库，避免 GPL 等强传染协议
- 最小化依赖数量，避免引入未使用的大型库
- 优先选择维护活跃、社区成熟的项目

### 3.2 开发依赖清单

`requirements-dev.txt`：
```
-r requirements.txt
pytest
pytest-asyncio
pytest-cov
vcrpy
respx
ruff
black
```

| 依赖 | 用途 |
|---|---|
| pytest | 测试框架 |
| pytest-asyncio | 异步测试支持 |
| pytest-cov | 覆盖率统计 |
| vcrpy | 录制/回放 HTTP 响应（爬虫层测试） |
| respx | mock httpx 响应（下载引擎测试） |
| ruff | Lint 检查 |
| black | 代码格式化 |

### 3.3 依赖升级原则

1. **最小化依赖**：不引入未使用的库，定期审查 `requirements.txt` 清理冗余
2. **宽松协议优先**：新增依赖前确认其 License 兼容性（GPL 类协议一律拒绝）
3. **定期更新**：每月执行一次 `pip list --outdated` 审查，安全漏洞（CVE）及时修复
4. **版本锁定**：发布版本前用 `pip freeze > requirements.lock` 锁定确切版本（仅用于复现打包，不作为日常开发依赖）
5. **破坏性变更评估**：升级主版本号前需评估 API 兼容性，在独立分支验证
6. **签名算法相关依赖谨慎升级**：`httpx` 升级可能影响请求行为，需充分回归测试

## 4. Git 工作流规范

### 4.1 分支策略

采用 **Git Flow** 简化变体：

| 分支 | 用途 | 保护规则 |
|---|---|---|
| `main` | 稳定发布分支，仅存放可发布代码 | 禁止直接 push，仅通过 PR 合入；需通过全部 CI 检查 + 至少 1 人 Review |
| `develop` | 开发集成分支，所有功能分支的合入目标 | 禁止直接 push，仅通过 PR 合入；需通过 CI 检查 |
| `feature/*` | 新功能开发分支 | 从 `develop` 切出，完成后 PR 回 `develop` |
| `fix/*` | Bug 修复分支 | 从 `develop` 切出，完成后 PR 回 `develop` |
| `release/*` | 发布准备分支 | 从 `develop` 切出，完成后 PR 回 `main` 与 `develop` |
| `hotfix/*` | 紧急生产修复分支 | 从 `main` 切出，完成后 PR 回 `main` 与 `develop` |

**分支拓扑示意**：
```
main     ──●──────────────●────────● (v1.0.0)
            \             /│
develop      ●──●──●──●──●  │ (集成分支)
              \  │   │  /   │
feature/x      ●─┘   │  └───● (release/1.0.0)
                     │
fix/y               ●┘
```

### 4.2 分支命名规则

| 分支类型 | 命名格式 | 示例 |
|---|---|---|
| 功能分支 | `feature/<简短描述>` | `feature/cookie-pool-manager` |
| 修复分支 | `fix/<简短描述>` | `fix/range-download-overflow` |
| 发布分支 | `release/<版本号>` | `release/1.0.0` |
| 热修复分支 | `hotfix/<简短描述>` | `hotfix/signer-crash` |
| 文档分支 | `docs/<简短描述>` | `docs/cookie-tutorial` |
| 重构分支 | `refactor/<简短描述>` | `refactor/scheduler-logic` |

**命名规则**：
- 全小写，使用 `-` 或下划线连接单词
- 描述应清晰反映分支目的，避免无意义名称如 `feature/1`、`fix/xxx`
- 不包含 issue 编号在分支名中（在 PR 描述中引用）
- 分支名长度建议 ≤ 40 字符

### 4.3 Commit 规范

采用 [Conventional Commits](https://www.conventionalcommits.org/) 规范。

#### 4.3.1 Commit Message 格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

#### 4.3.2 Type 清单

| Type | 含义 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(downloader): 支持单文件分块续传` |
| `fix` | Bug 修复 | `fix(signer): 修复 msToken 生成空指针异常` |
| `docs` | 文档变更 | `docs: 更新 Cookie 教程截图` |
| `refactor` | 重构（不改变功能） | `refactor(scheduler): 抽取任务队列为独立类` |
| `test` | 测试相关 | `test(signer): 新增 X-Bogus 已知用例` |
| `chore` | 杂项（构建、依赖、配置） | `chore(deps): 升级 httpx 至 0.28` |
| `style` | 代码风格（格式化，不影响逻辑） | `style: black 格式化` |
| `perf` | 性能优化 | `perf(downloader): 优化进度信号节流` |
| `ci` | CI/CD 配置 | `ci: 新增 gitleaks 安全扫描 Job` |
| `build` | 构建系统/依赖 | `build: 更新 PyInstaller 打包配置` |
| `revert` | 回滚提交 | `revert: 回滚 msToken 算法变更` |

#### 4.3.3 Scope 清单（建议）

| Scope | 对应模块 |
|---|---|
| `signer` | `crawlers/signer/` |
| `url_parser` | `crawlers/url_parser.py` |
| `video_parser` | `crawlers/video_parser.py` |
| `user_home` | `crawlers/user_home_crawler.py` |
| `http_client` | `crawlers/http_client.py` |
| `downloader` | `downloader/` |
| `scheduler` | `downloader/scheduler.py` |
| `database` | `app/database.py` |
| `models` | `app/models.py` |
| `ui` | `ui/` |
| `deps` | 依赖管理 |

#### 4.3.4 Subject 规则

- 使用祈使句（中文用动词开头，如"新增"、"修复"、"更新"）
- 首字母不大写（中文不适用）
- 结尾不加句号
- 长度建议 ≤ 50 字符

#### 4.3.5 Body 规则

- 解释"为什么"而非"做了什么"（diff 已说明做了什么）
- 每行 ≤ 72 字符
- 可包含多个段落，用空行分隔

#### 4.3.6 Footer 规则

- **BREAKING CHANGE**：破坏性变更需在 footer 标注 `BREAKING CHANGE: <描述>`
- **关闭 Issue**：`Closes #123`、`Fixes #456`

#### 4.3.7 完整示例

```
feat(downloader): 支持单文件分块续传

使用 httpx Range 请求实现断点续传，下载中断后可从已下载
字节数继续，避免重新下载。

- 临时文件以 .part 后缀保存
- 每 5 秒持久化 downloaded_bytes 到 SQLite
- 完成后重命名为最终文件名

Closes #42
```

```
fix(signer): 修复 msToken 生成空指针异常

当输入参数为空字典时，msToken 模块未做空值检查导致抛出
AttributeError。增加参数校验。

BREAKING CHANGE: Signer.sign() 现在对空参数抛出 ValueError
而非 AttributeError
```

### 4.4 PR 规范

#### 4.4.1 PR 标题格式

PR 标题与 Commit Message 的首行格式一致：
```
<type>(<scope>): <subject>
```

示例：
- `feat(downloader): 实现单文件分块续传`
- `fix(signer): 修复 msToken 空指针异常`
- `refactor(scheduler): 抽取任务队列为独立类`

#### 4.4.2 PR 描述模板

```markdown
## 变更描述

<!-- 简述本 PR 做了什么，为什么做 -->

## 变更类型

- [ ] 新功能（feat）
- [ ] Bug 修复（fix）
- [ ] 重构（refactor）
- [ ] 文档（docs）
- [ ] 测试（test）
- [ ] 杂项（chore）

## 关联 Issue

Closes #

## 测试情况

- [ ] 新增/更新了对应的单元测试
- [ ] 本地运行 `pytest` 全部通过
- [ ] 覆盖率满足要求（行 ≥ 80%，方法 ≥ 30%）
- [ ] 签名算法变更已附带已知输入/输出对测试用例（如适用）

## 安全检查

- [ ] 未在代码/测试/日志中硬编码 Cookie
- [ ] VCR.py fixture 已擦除敏感头（如适用）
- [ ] 未引入新的敏感依赖

## 截图 / 录屏

<!-- UI 变更需附截图，其他变更按需 -->

## 检查清单

- [ ] 代码已通过 `ruff check .`
- [ ] 代码已通过 `black --check .`
- [ ] commit message 遵循 Conventional Commits 规范
- [ ] 已更新相关文档（如适用）
```

#### 4.4.3 Review 要求

| PR 类型 | Review 人数 | 额外要求 |
|---|---|---|
| 普通功能/修复 | ≥ 1 人 | - |
| 签名算法变更 | ≥ 2 人 | 必须包含项目维护者 Review |
| 数据库 schema 变更 | ≥ 2 人 | 必须附带迁移脚本与回滚方案 |
| CI/CD 配置变更 | ≥ 1 人 | - |
| 依赖升级（主版本） | ≥ 2 人 | 必须附带兼容性验证报告 |

**Review 要点**：
- 代码是否符合规范（命名、类型注解、文档字符串）
- 是否有 Cookie / 密钥硬编码
- 测试是否充分覆盖（含边界条件）
- 是否引入循环依赖
- 是否有性能隐患（如主线程阻塞操作）
- 是否符合设计文档的分层职责边界

#### 4.4.4 合并策略

- **默认使用 Squash Merge**：将 PR 的多个 commit 合并为一个，保持 main/develop 历史线性整洁
- 合并后的 commit message 使用 PR 标题（Conventional Commits 格式）
- **禁止 Fast-forward 合并**：保留合并记录便于追溯
- **禁止 Rebase 合并**：除非 PR 仅含单个完美 commit 且经 Reviewer 同意
- 合并后**删除源分支**（feature/fix 分支不保留）

## 5. 代码规范

### 5.1 Python 代码风格

- 遵循 [PEP 8](https://peps.python.org/pep-0008/) 基础风格
- 使用 **black** 自动格式化（行宽 88 字符）
- 使用 **ruff** 进行 lint 检查
- 缩进使用 4 个空格（禁止 Tab）
- 文件末尾保留一个空行
- 文件使用 UTF-8 编码，LF 换行符

**格式化命令**：
```bash
# 格式化全部代码
black .

# 检查格式（不修改文件，CI 用）
black --check .

# Lint 检查
ruff check .

# Lint 自动修复
ruff check . --fix
```

### 5.2 ruff lint 规则集

启用规则集（见 3.4.4 节配置）：

| 规则集 | 说明 |
|---|---|
| `E` / `W` | pycodestyle 错误与警告 |
| `F` | pyflakes（未使用变量、未定义变量等） |
| `I` | isort（import 顺序） |
| `B` | flake8-bugbear（常见陷阱） |
| `C4` | flake8-comprehensions（推导式优化） |
| `UP` | pyupgrade（使用现代 Python 语法） |
| `N` | pep8-naming（命名规范） |
| `SIM` | flake8-simplify（代码简化） |
| `RUF` | ruff 特有规则 |

**忽略规则**：
- `E501`：行长度由 black 处理，ruff 不重复检查

### 5.3 import 顺序规范

由 ruff 的 isort 规则强制执行，顺序如下：

```python
# 1. 标准库
import os
import sys
from pathlib import Path

# 2. 第三方库
import httpx
from PySide6.QtCore import Signal, Slot
from PySide6.QtWidgets import QMainWindow

# 3. 项目模块（按 app → crawlers → downloader → worker → ui 排序）
from app.config import APP_DATA_DIR
from app.database import get_connection
from crawlers.exceptions import CookieInvalidError
from crawlers.signer import Signer
from downloader.scheduler import Scheduler
```

**规则**：
- 每组之间空一行
- 组内按字母顺序排序
- 使用 `from x import y` 优先于 `import x.y`
- 禁止使用通配符 `from x import *`
- 项目内部模块在 `known-first-party` 中声明

### 5.4 命名规范

遵循 [PEP 8](https://peps.python.org/pep-0008/) 命名约定，由 ruff 的 `N` 规则集强制：

| 类型 | 规范 | 示例 |
|---|---|---|
| 类 | PascalCase | `class TaskScheduler:` |
| 函数 / 方法 | snake_case | `def download_item(self):` |
| 变量 | snake_case | `download_dir = ...` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT = 3` |
| 模块文件名 | snake_case | `url_parser.py` |
| 包名 | snake_case（短小） | `crawlers`, `downloader` |
| 私有成员 | _前缀 | `self._internal_state` |
| 类型变量 | PascalCase（单字母大写可） | `T`, `TaskT` |
| 异常类 | PascalCase + Error 后缀 | `class CookieInvalidError(Exception):` |
| 信号名 | snake_case | `progress_updated = Signal(...)` |
| 枚举值 | UPPER_SNAKE_CASE | `Status.PENDING` |

### 5.5 类型注解要求

- **所有公开函数/方法必须有完整的类型注解**（参数 + 返回值）
- 私有辅助函数建议添加类型注解
- 使用 `from __future__ import annotations` 延迟注解求值（Python 3.11+ 已默认支持，但显式声明更清晰）
- 复杂类型使用 `typing` 模块或 Python 3.9+ 内置泛型

**示例**：
```python

def parse_url(text: str) -> dict[str, Any]:

async def fetch_user_posts(

class TaskItem:

```

## 6. 测试规范

### 6.1 测试 Cookie 使用规范

> 摘自设计文档第 9.1 节，并补充执行细则。

#### 6.1.1 Cookie 来源

- 测试所需 Cookie **由开发者自行从浏览器获取，不硬编码、不提交到仓库**
- 禁止在代码、测试用例、注释、日志中写入真实 Cookie 字符串
- 禁止将真实 Cookie 上传到任何外部服务（包括 CI 日志、Issue、PR 描述）

#### 6.1.2 存放方式

- 真实 Cookie 仅存放在本地 `.env` 文件
- `.env` 已加入 `.gitignore`，严禁提交
- CI 环境不读取 `.env`，所有 CI 测试基于 VCR.py 录制的 fixture

#### 6.1.3 测试后清除要求

- **测试全流程完成后必须清除 Cookie 痕迹**：测试脚本结束前主动删除 Cookie 引用
- CI 环境不留存任何 Cookie（CI 仅使用 fixture，不接触真实 Cookie）
- 本地手动测试结束后，建议清空 `.env` 中的 `DOUYIN_TEST_COOKIE` 字段
- 严禁将真实 Cookie 录入 VCR.py fixture

#### 6.1.4 VCR.py 录制规范

- 录制真实响应时**自动擦除敏感头**：`Cookie`、`Set-Cookie`、`Authorization`
- 配置 VCR.py 的 `filter_headers`：

```python
import vcr

my_vcr = vcr.VCR(
    filter_headers=["cookie", "set-cookie", "authorization"],
    filter_post_data_parameters=["cookie"],
    record_mode="once",
)
```

- 录制生成的 fixture 在提交前需**人工核对**，确保不含敏感字段
- fixture 存放在 `tests/fixtures/` 目录，文件名使用 `test_<模块>_<场景>.yaml` 格式

### 6.2 覆盖率要求

> 摘自设计文档第 9.2 节。

#### 6.2.1 全局指标

| 指标 | 要求 |
|---|---|
| 代码行覆盖率 | **≥ 80%** |
| 方法覆盖率 | **≥ 30%** |

#### 6.2.2 各模块覆盖率要求

| 模块 | 路径 | 行覆盖率要求 | 说明 |
|---|---|---|---|
| 签名算法 | `crawlers/signer/` | **≥ 90%** | 核心组件，最高标准 |
| 下载引擎 | `downloader/` | **≥ 80%** | 断点续传/重试逻辑关键 |
| 爬虫层 | `crawlers/` | **≥ 75%** | 依赖外部 API，用 VCR.py 录制回放 |
| 数据层 | `app/` | **≥ 80%** | SQLite 持久化逻辑 |
| 工作线程 | `worker/` | **≥ 70%** | asyncio 与信号桥接 |
| UI 层 | `ui/` | **不强制** | Qt 组件难单测，重点靠手动验收 |

#### 6.2.3 pytest-cov 配置

配置在 `pyproject.toml`（见 3.4.2、3.4.3 节）：

```toml
[tool.pytest.ini_options]
addopts = "--cov=. --cov-report=term-missing --cov-report=html --cov-fail-under=80"

[tool.coverage.run]
source = ["app", "crawlers", "downloader", "worker", "ui"]
branch = true
```

- `--cov-fail-under=80`：CI 中覆盖率低于 80% 时测试命令返回非零退出码，阻断合并
- 分支覆盖率（branch coverage）同时启用
- 覆盖率报告输出到 `htmlcov/`（HTML）与 `coverage.xml`（XML，供 CI 工具读取）

> 摘自设计文档第 9.5 节。

## 10. 协作流程规范

#### 10.1.3 任务分配流程

1. 维护者创建 Issue 并打标签
2. 开发者认领 Issue（在 Issue 中评论"我来处理"）
3. 开发者从 `develop` 切出对应分支
4. 开发完成后提交 PR，关联 Issue（`Closes #N`）
5. PR Review 通过后合并，Issue 自动关闭

### 10.2 代码 Review 流程

#### 10.2.1 Review 步骤

1. **自检**：开发者提交 PR 前自行核对检查清单（见 4.4.2）
2. **自动化检查**：CI 自动运行 lint、测试、安全扫描
3. **人工 Review**：至少 1 名 Reviewer 进行代码审查
4. **修改迭代**：根据 Review 意见修改，推送新 commit
5. **最终确认**：Reviewer 批准（Approve）
6. **合并**：维护者执行 Squash Merge

#### 10.2.2 Review 关注点

| 维度 | 检查内容 |
|---|---|
| 功能正确性 | 是否实现 Issue 描述的需求；边界条件处理 |
| 安全性 | 是否硬编码 Cookie/密钥；VCR fixture 是否擦除敏感头 |
| 测试充分性 | 是否覆盖正常/异常/边界路径；覆盖率达标 |
| 代码规范 | 命名、类型注解、文档字符串、import 顺序 |
| 架构合规 | 是否符合分层职责边界；是否引入循环依赖 |
| 性能 | 是否在主线程执行耗时操作；是否有内存泄漏风险 |
| 可维护性 | 代码可读性；是否过度设计 |

#### 10.2.3 Review 礼仪

- 对事不对人，评论聚焦代码而非作者
- 区分"必须修改"（blocking）与"建议"（suggestion）
- 对优秀代码给予肯定
- 及时响应 Review 意见（24 小时内）

### 10.3 签名算法更新流程

> 签名算法（`crawlers/signer/`）是最易失效的组件，需特殊应急流程。

#### 10.3.1 算法失效判断

- 用户反馈下载全部失败，`fail_reason` 集中为"Cookie 失效或被限流"
- 但 Cookie 测试通过（"测试 Cookie"按钮返回有效）
- 调用抖音 API 全部返回 461/412 或异常响应

#### 10.3.2 应急更新流程

```
1. 确认失效
   ├─ 多个用户反馈 + 维护者本地验证
   └─ 确认签名算法失效（非 Cookie 问题）

2. 切 hotfix 分支
   └─ git checkout -b hotfix/signer-fix main

3. 更新算法
   ├─ 参考 Evil0ctal/Douyin_TikTok_Download_API 最新实现思路
   ├─ 仅修改 crawlers/signer/ 下对应子模块
   ├─ 不影响其他组件（接口签名 sign(url, params) -> dict 保持不变）
   └─ 更新 tests/data/known_signer_vectors.json 中的已知用例

4. 本地验证
   ├─ pytest tests/test_signer/ -v
   ├─ 用真实 Cookie 手动测试（验证签名有效性）
   └─ 在 .env 配置 Cookie，运行集成测试 pytest -m integration

5. 提交 PR
   ├─ PR 标题：fix(signer): 更新 XXX 签名算法以适配抖音最新风控
   ├─ 至少 2 人 Review（含项目维护者）
   └─ 必须附带已知输入/输出对测试用例

6. 紧急发布
   ├─ 合并到 main
   ├─ 打 hotfix tag（如 v1.0.1）
   ├─ 触发 CD 流程打包发布
   └─ 在 GitHub Release 说明中标注"修复签名算法失效"

7. 同步 develop
   └─ 将 hotfix 分支合并回 develop
```

#### 10.3.3 预防措施

- 签名算法模块**接口与实现解耦**：上层仅依赖 `Signer.sign()` 接口，算法变更不影响调用方
- 定期（每月）验证签名算法有效性，提前发现失效
- 监控 GitHub 上参考项目的算法更新动态
- `known_signer_vectors.json` 维护多组测试用例，覆盖算法边界

`.github/workflows/ci.yml`：

```yaml
name: CI

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [develop]

jobs:
  # ============================================================
  # Job 1: 代码检查
  # ============================================================
  lint:
    name: 代码检查（ruff + black）
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: 设置 Python 3.11
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"
      - name: 安装 lint 工具
        run: |
          python -m pip install --upgrade pip
          pip install ruff black
      - name: Ruff 检查
        run: ruff check .
      - name: Black 格式检查
        run: black --check .

  # ============================================================
  # Job 2: 安全扫描
  # ============================================================
  security:
    name: 安全扫描（gitleaks）
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: gitleaks 扫描
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          GITLEAKS_ENABLE_COMMENTS: true

  # ============================================================
  # Job 3: 单元测试
  # ============================================================
  test:
    name: 单元测试（pytest + 覆盖率）
    runs-on: windows-latest
    needs: [lint, security]
    steps:
      - uses: actions/checkout@v4
      - name: 设置 Python 3.11
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"
      - name: 安装依赖
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements-dev.txt
      - name: 运行测试
        run: pytest
      - name: 上传覆盖率报告
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: htmlcov/
          retention-days: 14

  # ============================================================
  # Job 4: 构建验证
  # ============================================================
  build:
    name: 构建验证（PyInstaller 打包）
    runs-on: windows-latest
    needs: test
    steps:
      - uses: actions/checkout@v4
      - name: 设置 Python 3.11
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"
      - name: 安装依赖
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pyinstaller
      - name: PyInstaller 打包
        run: |
          pyinstaller --onedir --windowed --name DouyinCatcher `
            --icon assets/icon.ico `
            --add-data "ui/assets;ui/assets" `
            --add-data "assets;assets" `
            --noconfirm `
            main.py
      - name: 验证产物
        shell: pwsh
        run: |
          if (-not (Test-Path "dist\DouyinCatcher\DouyinCatcher.exe")) {
            Write-Error "打包产物不存在"
            exit 1
          }
          Write-Host "打包成功"
```

```pascal
[Run]
Filename: "{app}\{#MyAppExeName}"; Description: "{cm:LaunchProgram,{#MyAppName}}"; Flags: nowait postinstall skipifsilent

[UninstallDelete]
; 卸载时清理日志（用户数据 data.db 保留）

[Code]

  Result := True;
```

**使用说明**：
1. 将脚本保存为项目根目录下的 `installer.iss`
2. 确保 PyInstaller 打包已完成，`dist\DouyinCatcher\` 目录存在
3. 安装 Inno Setup 6（含中文语言包）
4. 执行：`"%ProgramFiles(x86)%\Inno Setup 6\ISCC.exe" installer.iss`
5. 产物位于 `dist\DouyinCatcher_Setup.exe`

**注意事项**：
- `AppId` 为固定 GUID，发布后**不可更改**（影响升级识别）
- 卸载时不删除 `%APPDATA%/DouyinCatcher/`（用户数据保留）
- 中文语言包需 Inno Setup 安装时勾选，或手动下载 `ChineseSimplified.isl` 放入 `compiler:Languages\`
- 每次发布前更新 `#define MyAppVersion` 与 `pyproject.toml` 版本号一致
