# Issue 2：下载任务完成状态与进度条显示异常设计

## 目标

修复 v0.3.1 Issue 2 中的全部现象：任务完成后不能稳定显示绿色 100% 进度、接近完成的任务被错误标记为完成、“清空已完成”影响进行中任务，以及 WebSocket/刷新造成的偶发状态回退。

## 现状与根因

- `backend/api/ws.py` 只查询并推送 `downloading` 任务项，因此前端不会通过 WebSocket 收到 `completed` 或 `failed` 终态。
- `backend/app.py` 创建 `Scheduler` 时未注册完成、失败和进度回调，下载器虽然持久化任务项状态，但父任务统计和状态不会可靠同步。
- REST 返回的进度只由字节数计算，完成项在字节数未及时写回或总大小未知时可能不是 100%。
- 前端 Store 在异步 `loadTasks()` 完成后整体替换列表，可能用较早的 REST 响应覆盖较新的 WebSocket 状态。
- “清空已完成”依赖父任务状态，父任务状态落后时会漏删；同时刷新竞态可能让进行中项显示异常。

## 设计

### 1. 后端状态闭环

在 Sidecar 创建 `Scheduler` 时注册回调，并在回调中统一维护任务项与父任务的展示统计：

- 完成回调：将任务项状态确认为 `completed`，进度按完成状态视为 100%，重新计算父任务的完成数和展示状态。
- 失败回调：将任务项状态确认为 `failed`，保存失败原因，重新计算父任务的展示状态。
- 进度回调：持久化进度后重新计算父任务统计；只在真实完成条件下切换任务项为 `completed`。
- 父任务状态从其全部任务项推导：存在 pending/downloading/paused 时不标记 completed；所有项 completed 时为 completed；无活动项且存在 failed 时为 failed。

父任务（Task）只作为计数和状态标记，不参与任何具体任务项行为。任务项的暂停、恢复、重试、删除、入队、去重和下载执行均只依据任务项自身状态与 ID，不能因为父任务状态变化而被取消、阻塞、重置或跳过。状态同步函数只更新展示统计，不反向修改任务项或调度器行为。

### 2. REST 与 WebSocket 状态一致

- 任务项 API 返回时：状态为 `completed` 时强制返回 `progress=100`；其它状态按实际字节数计算并限制在 0 到 100 之间。
- WebSocket 每轮读取所有具有可展示状态的任务项，而不只读取 `downloading`，推送状态、进度、字节数和任务项 ID；完成项保持 100%，避免终态只在刷新后出现。
- WebSocket 推送失败或无效记录时不改变数据库状态，异常只记录日志并继续下一轮。

### 3. 前端状态与刷新竞态保护

- Store 应用 WebSocket 更新时，完成状态强制归一为 100%；其它状态保留服务端进度。
- `loadTasks()` 合并 REST 结果而非无条件覆盖已有实时状态：当已有项拥有较新的终态或更高进度时，不被较旧响应回退；删除的项仍以服务端结果为准。
- “清空已完成”完成后重新加载一次；进行中项的状态和进度不由清理操作修改。
- `TaskItem` 继续以状态决定进度条样式，completed 始终使用 success 变体并显示“完成”。

## 错误处理

- 回调遇到不存在的任务项时记录警告并忽略，不阻塞调度器。
- 父任务不存在或数据库更新异常时记录错误；下载任务本身的最终状态仍由任务项保存结果决定。
- 前端 WebSocket 断开时保留当前状态，重连后由 REST 刷新补齐；单次 REST 加载失败不清空现有列表。

## 测试与验收

后端增加或更新测试覆盖：

1. 下载成功后任务项为 `completed`，API 进度为 100；
2. 多任务项完成时父任务 `completed_items` 和 `status` 正确；
3. 失败项不会被标记为完成，父任务状态为 `failed`（无活动项时）；
4. 进行中任务与已完成任务并存时，清空已完成只删除完成任务；
5. WebSocket 推送 completed/failed 终态及归一化进度；
6. 进度 95/97/100 的中间状态不会因刷新或清理被错误完成。

前端执行 TypeScript 检查和生产构建，确认 Store 合并逻辑和组件类型正确。验收标准是：任务完成后无需点击“清空已完成”即可稳定显示绿色 100%；清理操作不改变任何未完成任务的状态、进度或运行；刷新、WebSocket 重连后状态最终一致。
