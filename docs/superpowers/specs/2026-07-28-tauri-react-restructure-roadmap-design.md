## 1. 背景

当前项目的桌面端前端基于 PySide6 / Qt 实现，已经完成下载、解析、Cookie 管理、设置、引导等核心页面，但在长期使用中逐渐暴露出一组结构性问题：

- UI 现代感不足，自绘标题栏、焦点态、阴影、动画等细节开发成本高
- 页面交互与调试效率偏低，视觉与状态管理能力受 Qt 约束较多
- 打包体积、启动体验、调试体验和未来扩展空间不理想
- 非技术用户对桌面工具的第一印象与长期使用体验仍有提升空间

在不改变 Python 核心能力的前提下，前端改造为 **Tauri + React**，可以把界面层迁移到 Web 技术栈，同时继续保留现有 Python 爬虫、下载、SQLite 数据层作为 sidecar 服务，属于当前项目最务实的演进方向。

---

## 2. 设计目标

### 2.1 总目标

将当前 PySide6 桌面前端重构为 **Tauri + React + TypeScript + Tailwind CSS**，Python 作为 **FastAPI sidecar** 保留现有业务能力，形成“前端壳 + Python 服务”的新架构。

### 2.2 具体目标

- 先冻结 UI 原型和视觉方案，再进入接口与页面接入
- 让页面职责更清晰，减少 Qt 时代累积的交互耦合
- 保持 Python 后端逻辑不重写，只做服务化封装
- 逐步迁移，避免一次性大爆炸式重构
- 将原 v0.2.3 / v0.2.4 的 Qt 实施路线替换为新的迁移路线

---

## 3. 技术路线

### 3.1 前端

- 桌面壳：Tauri
- 页面框架：React 18 + TypeScript
- 样式体系：Tailwind CSS
- 组件体系：shadcn/ui + 少量项目级自定义组件
- 路由：React Router
- 服务状态：TanStack Query
- 客户端状态：Zustand
- 实时通信：WebSocket

### 3.2 后端

- Python 保留为 sidecar 进程
- 建议服务框架：FastAPI + Uvicorn
- 业务能力继续复用现有代码：签名、解析、抓取、下载、数据库、Cookie 管理
- 前后端通过 `localhost` 的 HTTP / WebSocket 通信

### 3.3 桌面能力

- Tauri 负责窗口、系统托盘、文件对话框、快捷键、自动更新、进程生命周期
- Python 负责业务逻辑和数据持久化
- 前端负责所有可视化、交互、状态展示

## 4. UI 设计原则

### 4.1 冻结点

用户已经明确要求：**UI 原型布局与外观必须在所有任务开始前决定**。因此本次重构采用“先原型、后接入”的策略。

在 `v0.2.3` 阶段冻结以下内容：

- 主窗口布局
- 导航结构
- 页面信息架构
- 颜色 / 字体 / 间距 / 圆角 / 阴影
- 组件状态规范
- 空状态 / 加载态 / 错误态
- 首次引导流程骨架

后续各里程碑只做数据接入、行为接入和细节调整，不再反复推翻 UI 基础方案。

### 4.2 视觉方向

- 采用浅色、克制、信息密度适中的工具型界面
- 保持品牌紫作为主色，辅以绿色成功、红色失败、黄色警告、蓝色信息
- 页面结构保持清晰，避免装饰性卡片过多
- 关键操作突出，次要操作收纳
- 对非技术用户保持明确、可预测的反馈

### 4.3 页面原型边界

初版 React 原型至少包括：

- 下载任务页
- 批量抓取页
- 主页抓取页
- Cookie 配置页
- 设置页
- 首次引导页

这些页面在 v0.2.3 中先完成 mock 数据交互，之后按里程碑接入真实服务。

## 5. 新旧路线切换

### 5.1 保留

- Python 爬虫、下载、数据库逻辑
- Cookie 管理核心能力
- 下载断点续传与重试策略
- 现有业务约束与面向非技术用户的错误文案原则

### 5.2 替换

- PySide6 UI
- Qt 信号/槽跨线程 UI 架构
- Qt 自绘窗口与样式体系
- 旧的 Qt 页面实现文件
- 旧的 v0.2.3 / v0.2.4 Qt 实施路线文档

### 5.3 迁移原则

- 先建立新壳和设计系统，再做业务接入
- 先接低风险页面，再接高频页面
- 先打通只读与查询能力，再接控制能力
- 先保证可运行，再做体验优化

## 6. 8 个里程碑规划

### v0.2.3 - 前端原型与设计系统搭建

目标：完成 Tauri + React 前端原型，冻结视觉与页面框架。

范围：
- Tauri + React + TypeScript + Tailwind 脚手架
- 设计 token 建立
- shadcn/ui 基础组件接入
- 主窗口框架、导航、标题栏、布局骨架
- 6 个页面 mock 原型
- 基础动画、Toast、空状态、加载态

### v0.2.4 - Python Sidecar 服务层

目标：将现有 Python 能力封装成可供前端调用的服务。

范围：
- FastAPI 服务结构
- REST API：下载 / 解析 / Cookie / 配置
- WebSocket 进度通道
- 健康检查与启动管理
- 旧 Qt worker 桥接替换/收敛

### v0.2.5 - 下载任务页对接

目标：下载任务页从 mock 切换到真实数据与操作。

范围：
- 任务列表查询
- 实时进度显示
- 暂停 / 恢复 / 重试 / 清空
- 搜索与空状态

### v0.2.6 - 抓取与解析页对接

目标：批量抓取页与主页抓取页接入真实 API。

范围：
- 批量链接解析
- 主页抓取与过滤
- 勾选下载与导入文件
- 加载态 / 错误态

### v0.2.7 - Cookie 配置、设置与引导页对接

目标：剩余基础页面完成真实功能接入。

范围：

### v0.2.9 - 联调测试、缺陷修复与性能优化

范围：

## 8. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 通信层复杂化 | 前后端分离后出现接口/进度同步问题 | 先统一 API 契约，再接页面 |
| UI 返工 | 视觉和信息架构未冻结会导致重复修改 | v0.2.3 阶段一次性定稿 |
| Sidecar 生命周期 | Python 服务崩溃或端口冲突会影响整体可用性 | 做健康检查与自动重启 |
| 打包复杂度上升 | Tauri + Python sidecar 双打包 | v0.3.0 单独收口 |
| 迁移成本高 | 现有 Qt 页面不能直接复用 | 通过分阶段迁移控制风险 |
