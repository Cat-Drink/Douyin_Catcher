# v0.3.0 合规与归属更新设计

- **分支**：`update/v0.3.0-compliance`
- **基线**：`v0.3.0`（当前 `master` 的发布后修复状态）
- **目标**：在不改变爬取、签名和下载业务行为的前提下，修正项目归属信息，补齐第三方许可说明，记录上游参考关系，并对高风险实现与测试数据来源形成可审计证据。
- **范围**：本轮同时覆盖 Evil0ctal/Douyin_TikTok_Download_API 相关合规问题和打包发布中的第三方许可证清单问题。

## 1. 背景与现状

项目后端参考了 `Evil0ctal/Douyin_TikTok_Download_API` 的公开 API 使用方式和签名原理，但仓库检索未发现直接导入、依赖或 vendoring 上游源代码。项目自身使用 MIT 许可证；上游项目页面标示 Apache-2.0。当前主要问题如下：

1. `installer.iss` 的 `MyAppURL` 仍指向上游仓库，会造成安装器发布者/支持地址的归属混淆。
2. README 和签名模块有参考声明，但没有单独的第三方致谢/许可证说明；缺少对“不复制上游代码”的明确分发声明。
3. `tests/data/known_signer_vectors.json` 的来源和生成方式没有文件级说明；架构文档使用“从开源项目抓取参考”的表述，容易被误读为复制测试数据。
4. X-Bogus、A_Bogus、视频解析、主页分页是功能最接近上游的实现，缺少可复查的独立实现审查记录。
5. npm、Rust 和 Python 依赖会随桌面安装包或 sidecar 分发，但没有集中式第三方许可证清单。

## 2. 设计原则与非目标

### 原则

- **不改变运行时行为**：不重写签名算法，不改变 API 参数、响应解析、下载策略或风控处理。
- **来源透明**：区分公开事实/API/算法原理、独立实现和实际第三方代码；不作无法证明的法律断言。
- **可审计**：每项修改都有对应文档、测试或检查命令，并使用独立 Git 提交。
- **分发完整**：安装包中的第三方组件应有可定位的许可证信息。

### 非目标

- 不对上游项目作法律定性，不替代律师意见。
- 不因 API 字段或公开算法原理相同而进行无必要的代码重构。
- 不引入新的运行时依赖，不改变许可证为 Apache-2.0，也不将可能的第三方代码重新标为 MIT。
- 不推送分支，不创建 PR。

## 3. 更新项设计

### 3.1 修正应用归属元数据

修改 `installer.iss`：将 `MyAppURL` 改为本项目官方仓库 `https://github.com/Cat-Drink/Douyin_Catcher`，使 `AppPublisherURL` 和 `AppSupportURL` 与 README、发布工作流一致。添加一个针对该值的静态回归检查，避免以后打包配置重新指向上游。

**验收**：仓库中安装器的发布者/支持 URL 不再出现上游仓库，且检查命令能覆盖该配置。

### 3.2 增加参考项目与第三方归属说明

新增 `THIRD-PARTY-NOTICES.md`，包含：

- 上游项目名称、链接和其声明的 Apache-2.0 许可证链接；
- 明确本项目参考公开设计/原理，未将上游源码作为依赖、导入或 vendoring；
- 本项目 MIT 许可证只适用于本项目自有代码，不覆盖实际存在的第三方内容；
- 分发时保留本文件和 `LICENSE`。

README 的许可证章节增加链接，避免只在正文中出现一次参考声明。

**验收**：参考关系、许可证边界和不背书表述清楚，且不声称上游对本项目授权或背书。

### 3.3 记录签名测试向量来源

新增 `tests/data/README.md`，说明 `known_signer_vectors.json` 是本项目测试输入/输出契约，记录生成方式、固定时间戳和维护规则；不得从上游仓库复制受版权保护的测试文件或响应样例。将架构文档中“从开源项目抓取参考”改为“依据公开原理和本项目实现独立生成/核验”，与实际可证明事实一致。

不修改测试向量值，不改变签名实现，不把未经核实的上游来源写成事实。如果未来某个向量确实来自第三方，则必须在向量文件中保留来源和对应许可证，而不是继续使用当前的无来源表述。

**验收**：测试数据目录具有来源说明；文档中不再使用会暗示直接复制上游测试数据的措辞；现有签名测试保持通过。

### 3.4 形成高风险实现独立性审查记录

新增 `docs/compliance/v0.3.0-code-origin-audit.md`，覆盖：

- `crawlers/signer/xbogus.py`
- `crawlers/signer/abogus.py`
- `crawlers/video_parser.py`
- `crawlers/user_home_crawler.py`
- `crawlers/api_spec.py`

审查记录只陈述可验证事实：无上游导入/依赖/vendoring，代码的公开 API、字段和算法原理相似属于功能事实；指出必须持续人工比对的风险边界；记录本次检查使用的 grep、依赖清单和 Git 历史证据。对于无法仅靠静态检查证明的“代码完全独立”，明确标记为未作法律保证。

**验收**：审查记录列出文件、证据、残余风险和后续规则，不伪造逐行相似度结论。

### 3.5 生成发布依赖许可证清单

新增 `scripts/generate_license_report.py`，以仓库锁文件和 Python 项目元数据为输入，生成 `licenses/THIRD-PARTY-LICENSES.md`：

- Python：记录 `requirements.txt` / `requirements-dev.txt` 中的直接依赖及其版本约束，许可证信息以包元数据可查询为准；
- npm：读取 `frontend/package-lock.json` 中锁定包的 `license` 字段并按包名/版本排序；
- Rust：读取 `frontend/src-tauri/Cargo.lock` 的包名/版本，并为许可证状态保留“需从 crate 元数据核实”的明确标记，避免猜测许可证；
- 报告注明生成时间、输入文件和未能自动确认的项目。

脚本只生成审计清单，不改变构建流程或运行时。为避免把不完整清单误当作合规保证，报告中将“自动发现”和“需人工核实”分开，并保留各依赖的来源定位。必要时补充 `licenses/README.md` 说明更新命令和发布前核验要求。

**验收**：脚本可重复运行；报告包含 npm/Rust/Python 三类依赖；任何缺少许可证字段的组件都显式列出而不是静默忽略。

### 3.6 增加合规回归检查

新增针对合规约束的测试/检查，至少覆盖：

- `installer.iss` 不包含上游仓库作为 `MyAppURL`；
- 第三方归属文件存在且包含上游链接、Apache-2.0 链接和非 vendoring 声明；
- 测试数据来源说明存在；
- 许可证报告可由脚本重新生成，且工作树差异可审查。

检查应使用标准库或现有开发依赖，避免为一次性合规检查引入新运行时包。

## 4. 提交策略

按以下顺序进行细粒度提交，每个提交只解决一个主题：

1. `docs(compliance): add v0.3.0 update design`
2. `fix(installer): restore project repository metadata`
3. `docs(compliance): add upstream attribution notice`
4. `docs(tests): document signer vector provenance`
5. `docs(compliance): record crawler code-origin audit`
6. `chore(licenses): add dependency license report generator`
7. `docs(licenses): add generated third-party inventory`
8. `test(compliance): add release metadata regression checks`

提交前不 squash、不推送；每个提交后检查 `git diff --check`，阶段性运行相关测试，最后运行完整测试和许可证报告生成检查。

## 5. 风险与回滚

- **许可证字段缺失或网络不可用**：脚本不猜测许可证，报告标记待核实；不阻塞代码测试，但阻止把报告描述为完整法律意见。
- **上游代码相似性争议**：本轮只记录证据，不通过改名或格式化掩盖相似性；如人工比对发现实质复制，应单独隔离、补充原许可证或重写后再发布。
- **安装器构建环境不可用**：使用静态检查验证 URL；若本机具备 Inno Setup，再执行实际编译验证。
- **回滚**：每个主题独立提交，可按提交粒度回退；不回退基线 v0.3.0。
