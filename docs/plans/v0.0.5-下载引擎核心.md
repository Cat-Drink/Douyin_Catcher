## 2. 里程碑概述

### 2.1 里程碑定位

本里程碑是 10 个里程碑中的**第 5 个**，实现下载引擎核心。下载引擎是整个应用的数据落地枢纽，承接爬虫层解析出的直链，完成文件下载、断点续传、失败重试、并发调度与进度汇报。

```
里程碑序列（10 个）：
  v0.0.1 数据层        ✅ 前置依赖（已完成）
  v0.0.2 ...           （中间里程碑）
  v0.0.5 下载引擎核心  ◄── 本里程碑
  ...
  v1.0.0 正式发布
```

### 2.2 前置依赖

| 依赖项 | 来源 | 说明 |
|---|---|---|
| 数据层 v0.0.1 | `app/` | 提供 `Task`、`TaskItem` 数据模型与 SQLite 持久化（`app/models.py`、`app/database.py`） |
| httpx | 第三方库 | 异步 HTTP 客户端，支持 Range 分块续传（`requirements.txt` 已声明） |
| respx | 开发依赖 | mock httpx 响应，用于下载引擎测试（`requirements-dev.txt` 已声明） |

**关键约束**：下载引擎**只依赖数据层，不依赖爬虫层**。下载引擎的输入是已解析完成的 `TaskItem`（含 `url` 直链），不关心 URL 如何获得。这一边界由设计文档第 5.6 节明确界定。

### 2.3 交付目标

| 目标 | 衡量指标 |
|---|---|
| 单项下载器可用 | 能流式下载文件、写入 `.part`、完成后重命名 |
| 断点续传可用 | `.part` 文件续传、Range 请求正确、进度持久化 |
| 失败重试可用 | 指数退避（2s/4s/8s）、3 次上限、4xx 不重试 |
| 暂停/恢复可用 | `asyncio.Task` 取消、status 流转、Range 续传 |
| 调度器并发控制 | `asyncio.Semaphore` 限制并发、图集子并发 |
| 进度节流可用 | 500ms 批量发送、Queue 去重 |
| 去重逻辑可用 | 已完成 aweme_id 不重复下载 |
| 质量达标 | pytest 全部通过、下载引擎行覆盖率 ≥ 80%、ruff/black 无报错 |

## 4. 设计依据与技术约束

### 4.1 数据模型依据（设计文档 4.1 节）

下载引擎直接读写的 `task_items` 表关键字段：

| 字段 | 类型 | 下载引擎用途 |
|---|---|---|
| `id` | INTEGER | 任务项唯一标识（进度信号、回调均用此 ID） |
| `aweme_id` | TEXT | 去重判断依据 |
| `url` | TEXT | 下载直链（无水印） |
| `type` | TEXT | `'video'`/`'image_set'`/`'long_video'`，决定单文件/图集下载逻辑 |
| `status` | TEXT | 状态机：`pending`→`downloading`→`completed`/`failed`/`paused` |
| `downloaded_bytes` | INTEGER | 断点续传已下载字节数 |
| `total_bytes` | INTEGER | 文件总大小（Content-Length） |
| `retry_count` | INTEGER | 已重试次数（上限 3） |
| `fail_reason` | TEXT | 失败原因 |
| `local_path` | TEXT | 完成后的本地文件路径 |
| `task_id` | INTEGER | 关联 `tasks.download_dir` 用于确定本地存储目录 |

### 4.2 下载流程依据（设计文档 5.2 节）

单项下载严格按以下 5 步执行：

1. 从 SQLite 取 `task_item`（status=pending/downloading），置为 `downloading`
2. 检查本地 `.part` 文件是否存在 → 读取已下载字节数 `downloaded_bytes`
3. 用 httpx 发 `Range: bytes={downloaded_bytes}-` 请求
4. 流式接收数据，每收到一块（64KB）：
   - 追加写入 `.part` 文件
   - 更新内存中的 `downloaded_bytes`
   - 每 5 秒或每 1MB 持久化一次 `downloaded_bytes` 到 SQLite
   - 进度信号由进度汇报协程统一节流发送（见 5.5）
5. 下载完成 → `.part` 重命名为最终文件 → status=completed → 发 `item_completed` 信号

### 4.3 失败重试策略依据（设计文档 5.3 节）

| 触发条件 | 处理 |
|---|---|
| 网络异常 / HTTP 5xx / 被风控限流（HTTP 461/412） | 触发重试：`retry_count += 1`，等待 `2^retry_count` 秒（2s/4s/8s 指数退避） |
| 达到 3 次重试仍失败 | `status=failed`，记录 `fail_reason`，发 `item_failed` 信号 |
| HTTP 4xx（非限流） | 直接失败，不重试（链接无效等） |

### 4.4 暂停/恢复依据（设计文档 5.4 节）

- **暂停**：调度器把目标项的 `asyncio.Task` 取消（`task.cancel()`），status 改为 `paused`，保留 `.part` 文件和 `downloaded_bytes`
- **恢复**：重新创建 `asyncio.Task`，从 `paused` → `downloading`，走 Range 续传

### 4.5 进度节流依据（设计文档 5.5 节）

- 下载引擎内部用 `asyncio.Queue` 缓存进度更新
- 一个专门的"进度汇报协程"每 500ms 从 Queue 取最新值，批量发一次 `progress_updated` 信号

### 4.6 并发控制依据（设计文档 2.4 节）

- 下载引擎用 `asyncio.Semaphore` 限制并发数，用户可配（默认 3，上限 10）
- 图集类型多图片在单项下载器内部再开子并发，也受总 Semaphore 约束

### 4.7 回调接口约束

- 进度信号、完成、失败信号**通过回调函数传递，不直接依赖 Qt**（设计文档 5.1 节的"进度信号发射器"在本里程碑中以回调形式实现，Qt 信号桥接由后续 `worker/` 里程碑完成）

### 4.8 测试约束（设计文档 9.5 节、规范文档 6.3 节）

- 下载引擎测试：mock httpx 响应，测试分块续传/重试/暂停逻辑
- 工具：pytest + respx
- 覆盖率要求：`downloader/` 行覆盖率 ≥ 80%
- 不打真实网络请求

## 5. 任务清单

本里程碑共 5 个任务，按依赖顺序执行。每个任务细化到文件、函数、参数与行为描述，**不包含实现代码**。

### 任务 1：进度信号节流器（`downloader/progress_reporter.py`）

#### 1.1 目标

实现进度更新的缓存与节流发送，避免每个 64KB 数据块都触发一次 UI 更新导致性能问题。严格遵循设计文档 5.5 节。

#### 1.2 文件清单

| 文件 | 类型 | 说明 |
|---|---|---|
| `downloader/progress_reporter.py` | 新建 | ProgressReporter 类与 ProgressUpdate dataclass |
| `downloader/__init__.py` | 新建/修改 | 导出 ProgressReporter、ProgressUpdate |

#### 1.3 数据结构

**`ProgressUpdate`（dataclass）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_item_id` | `int` | 任务项 ID |
| `downloaded_bytes` | `int` | 已下载字节数 |
| `total_bytes` | `int` | 文件总字节数 |

#### 1.4 类与函数清单

**`ProgressReporter` 类**

| 成员 | 签名 | 行为描述 |
|---|---|---|
| `__init__` | `(self, on_progress: Callable[[list[ProgressUpdate]], None], flush_interval_ms: int = 500) -> None` | 初始化回调函数、刷新间隔（默认 500ms）、内部 `asyncio.Queue`、最新值字典（按 task_item_id 去重）、汇报协程句柄 |
| `update` | `(self, task_item_id: int, downloaded_bytes: int, total_bytes: int) -> None` | 将进度更新放入内部 Queue（实际存入最新值字典，保证同一 task_item_id 只保留最新值，实现 Queue 去重） |
| `flush` | `(self) -> None` | 强制发送当前积累的所有进度更新（从最新值字典取出全部，组装成 list，调用 `on_progress` 回调） |
| `start` | `(self) -> None` | 启动专门的汇报协程（asyncio.create_task） |
| `stop` | `(self) -> None` | 停止汇报协程，flush 残留进度 |
| `_report_loop` | `(self) -> None`（async） | 汇报协程主循环：每 `flush_interval_ms` 毫秒 sleep 一次，醒来后调用 `flush()`；循环直至收到停止信号 |

#### 1.5 内部机制说明

1. **Queue 缓存**：`update()` 调用时不直接触发回调，而是更新内部最新值字典 `_latest: dict[int, ProgressUpdate]`（key=task_item_id），并向 `asyncio.Queue` 放入一个标记通知汇报协程有新数据
2. **去重**：同一 `task_item_id` 的多次 `update` 只保留最后一次的值，字典覆盖即可，实现"Queue 去重"
3. **批量发送**：汇报协程每 500ms 醒来，将字典中所有值打包成 `list[ProgressUpdate]`，调用 `on_progress` 回调一次性发送，发送后清空字典
4. **回调解耦**：`on_progress` 是普通可调用对象，不依赖 Qt 信号；后续 `worker/` 里程碑再桥接到 Qt 信号

#### 1.6 关键常量

| 常量 | 值 | 说明 |
|---|---|---|
| `DEFAULT_FLUSH_INTERVAL_MS` | `500` | 默认刷新间隔 500ms（设计文档 5.5 节） |

#### 2.6 `download()` 主流程（严格按设计文档 5.2 节）

```
download(task_item):
  1. 从 SQLite 取 task_item 最新状态，置为 downloading（_mark_status）
     - 若 type == 'image_set'：走 _download_image_set 分支
     - 否则（video / long_video）：走 _download_single_file 分支

  _download_single_file 流程（设计文档 5.2 节）:
    1. 检查 .part 文件是否存在
       - 存在 → 读取文件大小作为 downloaded_bytes（断点续传）
       - 不存在 → downloaded_bytes = 0
    2. 构造 Range 请求头：Range: bytes={downloaded_bytes}-
       - downloaded_bytes == 0 时不发 Range 头（完整下载）
    3. _send_range_request 发送请求
    4. 重试循环（最多 MAX_RETRY_COUNT 次）：
       a. 获取流式响应
       b. 从 Content-Length 与 downloaded_bytes 计算 total_bytes
       c. _stream_to_file 流式接收：
          - 每块 64KB (CHUNK_SIZE)
          - 追加写入 .part 文件（"ab" 模式）
          - downloaded_bytes += len(chunk)
          - 每 5 秒 或 每 1MB → _persist_progress 持久化到 SQLite
          - 每 chunk → progress_reporter.update() 更新进度（节流）
       d. 流结束 → _finalize_file 将 .part 重命名为最终文件
       e. _mark_status(task_item_id, 'completed', local_path=...)
       f. 返回 DownloadResult(success=True, local_path=...)
    5. 若步骤 a-d 抛出异常或返回错误状态码：
       - _should_retry 判断：
         * 网络异常 / 5xx / 461 / 412 → 重试
         * 4xx（非限流）→ 直接失败，不重试
       - 重试：retry_count += 1
         * 若 retry_count > MAX_RETRY_COUNT → _mark_status('failed', fail_reason=...)，返回 DownloadResult(success=False, error=...)
         * 否则 → _retry_with_backoff(retry_count) 等待 2^retry_count 秒，回到步骤 3
```

#### 2.7 图集下载流程（`_download_image_set`）

```
_download_image_set(task_item, urls, target_dir):
  - urls: 图集所有图片直链列表（从 task_item 解析或外部传入）
  - 对每个 url 创建一个 _download_single_file 子任务
  - 内部用 asyncio.gather 并发执行，每个子任务受总 semaphore 约束
    （通过 _download_single_file 内 acquire semaphore 实现）
  - 任一子任务失败 → 整个图集标记失败
  - 全部成功 → task_item.status = completed，local_path = target_dir
```

#### 2.8 取消（暂停）处理

- `_stream_to_file` 中捕获 `asyncio.CancelledError`
- 捕获后：`_persist_progress` 持久化当前 `downloaded_bytes`（确保进度不丢），保留 `.part` 文件
- 重新抛出 `CancelledError`，由调度器将 status 置为 `paused`
- **不**在 Downloader 内修改 status 为 paused（职责归调度器，见设计文档 5.4 节）

#### 2.9 重试判断细节（`_should_retry`，严格按设计文档 5.3 节）

| 情况 | 判断 | 返回 |
|---|---|---|
| `exception` 是 `httpx.NetworkError` / `httpx.ConnectError` / `httpx.ReadTimeout` 等 | 网络异常 | `True` |
| `status_code` 在 500-599 | HTTP 5xx | `True` |
| `status_code == 461` 或 `status_code == 412` | 被风控限流 | `True` |
| `status_code` 在 400-499（非 461/412） | HTTP 4xx 非限流 | `False`（直接失败不重试） |
| `status_code == 200` 且无异常 | 成功 | 不进入重试逻辑 |

| `MAX_CONCURRENT_LIMIT` | `10` | 并发上限 10（设计文档 2.4 节） |

#### 3.4 类与函数清单

**`Scheduler` 类**

| 成员 | 签名 | 行为描述 |
|---|---|---|
| `__init__` | `(self, max_concurrent: int = 3, http_client: httpx.AsyncClient \| None = None, on_item_completed: Callable[[int], None] \| None = None, on_item_failed: Callable[[int, str], None] \| None = None) -> None` | 初始化并发信号量（clamp 到 [1,10]）、httpx 客户端、回调、内部任务字典、待下载队列、ProgressReporter 实例、Downloader 实例 |
| `start` | `async (self) -> None` | 启动调度循环与 ProgressReporter 汇报协程 |
| `stop` | `async (self) -> None` | 停止调度，等待进行中的任务完成或取消，停止 ProgressReporter |
| `add_task_items` | `(self, items: list[TaskItem]) -> None` | 添加待下载项到内部队列；入队前执行去重检查（见 3.5） |
| `pause` | `async (self, task_item_id: int) -> None` | 取消对应 `asyncio.Task`（`task.cancel()`），status 置为 `paused`（设计文档 5.4 节） |
| `resume` | `async (self, task_item_id: int) -> None` | 重新创建 `asyncio.Task`，status 从 `paused` → `downloading`，走 Range 续传 |
| `pause_all` | `async (self) -> None` | 对所有进行中任务执行 `pause` |
| `resume_all` | `async (self) -> None` | 对所有 `paused` 任务执行 `resume` |
| `_schedule_loop` | `async (self) -> None` | 调度主循环：从队列取任务项，受 Semaphore 约束创建 `asyncio.Task` 执行下载 |
| `_run_download` | `async (self, task_item: TaskItem) -> None` | 单个任务项下载执行器：acquire semaphore → 调用 `downloader.download()` → 根据结果触发回调（on_item_completed / on_item_failed）→ release semaphore |
| `_is_already_completed` | `(self, aweme_id: str) -> bool` | 去重：查 `task_items` 是否已有该 aweme_id 的 `completed` 记录（设计文档 5.6 节） |
| `set_max_concurrent` | `(self, max_concurrent: int) -> None` | 动态调整并发数（clamp 到 [1,10]），重建 Semaphore |

#### 3.5 去重逻辑（设计文档 5.6 节）

- `add_task_items` 入队前，对每个 item 调用 `_is_already_completed(aweme_id)`
- 若已存在 `completed` 记录 → 跳过该项，不入队
- 若 `aweme_id` 为 None → 不去重（容错）

#### 3.6 暂停/恢复实现（设计文档 5.4 节）

**暂停 `pause(task_item_id)`：**
1. 从内部任务字典 `_tasks: dict[int, asyncio.Task]` 取出对应 Task
2. 调用 `task.cancel()` 触发 `CancelledError`
3. Downloader 内部捕获后持久化进度并保留 `.part`
4. 调度器将 `task_items.status` 置为 `paused`
5. 从 `_tasks` 字典移除

**恢复 `resume(task_item_id)`：**
1. 从 SQLite 取该 task_item（status 应为 `paused`）
2. 置 status 为 `downloading`
3. 创建新的 `asyncio.Task` 加入 `_tasks` 字典
4. Downloader 内部检测 `.part` 文件存在 → 走 Range 续传

#### 3.7 回调接口

| 回调 | 签名 | 触发时机 |
|---|---|---|
| `on_item_completed` | `Callable[[int], None]` | task_item_id 下载成功（Downloader 返回 success=True） |
| `on_item_failed` | `Callable[[int, str], None]` | task_item_id 下载失败（含 fail_reason） |

> 进度回调通过 `ProgressReporter.on_progress` 间接传递，不由 Scheduler 直接持有。

#### 3.8 与 ProgressReporter 集成

- Scheduler 在 `__init__` 中创建 `ProgressReporter` 实例（需外部传入 `on_progress` 回调或由 Scheduler 转发）
- `start()` 时同时启动 ProgressReporter 汇报协程
- `stop()` 时同时停止 ProgressReporter
- Downloader 通过 Scheduler 注入的 `progress_reporter` 引用调用 `update()`

### 任务 4：断点续传实现（融入任务 1-3）

#### 4.1 目标

实现设计文档 4.2 节描述的两层续传：任务队列续传 + 单文件分块续传。本任务不产生独立文件，而是将续传逻辑融入任务 1-3 的实现中。

#### 4.2 启动时恢复（任务队列续传，设计文档 4.2 节第 1 点）

**实现位置**：`Scheduler` 新增方法

| 成员 | 签名 | 行为描述 |
|---|---|---|
| `restore_pending_tasks` | `async (self) -> None` | 应用启动时调用：查询 `task_items` 中 `status IN ('pending', 'downloading', 'paused')` 的记录；将 `downloading` 状态重置为 `paused`（上次中断了）；将 `pending` 与 `paused` 项加入待下载队列 |

**恢复流程**：
1. 查询 `SELECT * FROM task_items WHERE status IN ('pending', 'downloading', 'paused')`
2. 对 `downloading` 记录执行 `UPDATE ... SET status='paused'`（重启后重置）
3. 对所有 `pending`、`paused` 记录调用 `add_task_items()` 加入队列
4. `paused` 项恢复时走 Range 续传（Downloader 检测 `.part` 文件）

#### 4.3 单文件续传（设计文档 4.2 节第 2 点）

**实现位置**：`Downloader._download_single_file` 与 `_get_part_path`

**续传流程**：
1. `.part` 文件存在 → `downloaded_bytes = part_path.stat().st_size`（读取文件大小）
2. HTTP Range 请求：`Range: bytes={file_size}-`
3. 追加模式（`"ab"`）写入 `.part` 文件
4. 服务端返回 206 Partial Content → 续传成功
5. 服务端返回 200（不支持 Range 或文件已变）→ 从头下载（`downloaded_bytes` 重置为 0）

#### 4.4 进度持久化（设计文档 4.2 节第 2 点 + 5.2 节第 4 步）

**实现位置**：`Downloader._stream_to_file` 与 `_persist_progress`

**持久化策略**（满足两个条件之一即触发）：
- 时间条件：距上次持久化超过 5 秒（`PERSIST_INTERVAL_SECONDS`）
- 字节条件：距上次持久化累计超过 1MB（`PERSIST_INTERVAL_BYTES`）

**持久化内容**：`UPDATE task_items SET downloaded_bytes=?, total_bytes=?, updated_at=? WHERE id=?`

**目的**：防止崩溃丢失进度，重启后可从 SQLite 读取 `downloaded_bytes` 作为续传起点。

## 8. 风险与注意事项

### 8.1 技术风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| httpx Range 请求服务端不支持（返回 200 而非 206） | 续传失效，从头下载 | Downloader 检测响应状态码，200 时重置 `downloaded_bytes=0` 从头下载 |
| `asyncio.CancelledError` 捕获时机不当 | 进度丢失或 status 流转错误 | Downloader 仅持久化进度并重抛 CancelledError，status 修改由 Scheduler 负责（职责分离） |
| 图集子并发与总 Semaphore 死锁 | 任务卡死 | 图集子任务 acquire 同一 Semaphore，确保 release 配对；测试覆盖图集场景 |
| SQLite 并发写入冲突（WAL 模式下） | 进度持久化失败 | WAL 模式已优化并发写；持久化操作短事务，必要时加 retry |
| respx mock 与真实 httpx 行为差异 | 测试通过但实际运行失败 | mock 响应尽量贴近真实（含 Content-Length、状态码、流式 body） |

### 8.2 实现注意事项

1. **职责边界**：Downloader 不修改 status 为 paused（归 Scheduler）；Scheduler 不直接处理 HTTP（归 Downloader）
2. **回调解耦**：所有对外通知用回调函数，不 import PySide6，确保下载引擎可独立测试
3. **.part 文件命名**：最终文件名 + `.part` 后缀，完成后 `os.rename` 去掉后缀
4. **图集 URL 来源**：图集类型的多个图片 URL 需从 `TaskItem` 获取（可能存于 url 字段以分隔符拆分，或元数据表）；本里程碑假设 `TaskItem` 已提供 URL 列表接口，具体存储方案由数据层定义
5. **时间 mock**：测试指数退避时务必 mock `asyncio.sleep`，否则单测耗时 14 秒（2+4+8）
6. **Range 头格式**：`Range: bytes={downloaded_bytes}-`（注意末尾的 `-`，表示从该字节到末尾）
7. **持久化节流**：`_persist_progress` 内部需对比上次持久化的时间与字节数，避免每 64KB 都写 SQLite

### 8.3 与后续里程碑的接口约定

| 接口 | 本里程碑提供 | 后续里程碑消费 |
|---|---|---|
| `Scheduler(on_item_completed=..., on_item_failed=...)` | 回调签名 | `worker/async_worker.py` 桥接到 Qt 信号 |
| `ProgressReporter(on_progress=...)` | 回调签名 | `worker/async_worker.py` 桥接到 `progress_updated` 信号 |
| `Scheduler.restore_pending_tasks()` | 启动恢复方法 | `worker/` 在应用启动时调用 |
| `Scheduler.add_task_items()` | 入队方法 | 爬虫层解析完成后通过 `worker/` 调用 |
