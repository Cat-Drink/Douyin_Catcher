## 一、基础运行层：先确保代码真的能执行

这是最低门槛，也是 AI 生成代码最容易出低级错误的地方。

1. 语法与拼写错误
   - 检查括号、引号、缩进是否匹配（尤其 Python、YAML 等缩进敏感语言）。
   - 核对变量名、函数名、类名的拼写一致性，AI 经常出现前后拼写不一致、单复数写错的问题。
   - 用 IDE 自带的语法高亮 / 报错、编译器、解释器直接跑一遍，快速定位语法级错误。
2. 导入与依赖真实性
   - 核对所有`import`/`include`的模块、包是否真实存在，AI 可能编造不存在的第三方库。
   - 检查调用的方法、属性是否属于对应类 / 模块，避免出现「模块根本没有这个函数」的幻觉问题。
3. 基础类型匹配
   - 强类型语言检查参数类型、返回值类型是否匹配；弱类型语言（如 Python/JS）重点看字符串与数字、列表与单个值的混用。
   - 警惕 AI 把字符串当数字运算、把 None 当成普通对象调用属性的常见错误。

## 二、逻辑正确性：核心功能是否真的解决问题

这是最核心的检查环节，AI 经常出现「看起来很对，实则答非所问」的情况。

1. 需求匹配度校验
   - 对照你的原始需求，确认代码是否完整覆盖了所有约束条件，有没有遗漏关键逻辑，或者额外加了一堆你不需要的功能。
   - 警惕 AI「过度脑补」：比如你只需要读取文件，它自动加了写入、删除、定时任务等无关逻辑。
2. 核心业务 / 算法逻辑推演
   - 把核心计算、判断逻辑单独拎出来，用已知结果的输入手动推演一遍，看输出是否符合预期。
   - 重点检查条件分支：`if/else`的边界条件是否正确，有没有漏分支、分支逻辑写反的情况。
3. 边界与极端输入
   - 空值场景：空列表、空字符串、None、空文件输入会不会报错。
   - 极值场景：最大值、最小值、零值、超长输入、超大文件是否会溢出或卡死。
   - 异常场景：格式错误的输入、非法参数会不会直接导致程序崩溃。
4. 流程与状态控制
   - 检查循环的终止条件，避免死循环；递归函数检查基线条件，防止栈溢出。
   - 核对变量作用域，避免全局变量被意外修改、循环内变量初始化位置错误。

## 三、安全合规层：排查潜在风险漏洞

AI 生成代码的安全意识普遍偏弱，很容易写出存在高危漏洞的代码。

1. 注入类风险
   - SQL 注入：检查是否直接拼接字符串构造 SQL 语句，必须使用参数化查询。
   - 命令注入：检查是否直接把用户输入拼接到系统命令中执行（如`os.system`、`exec`、`eval`）。
   - XSS / 模板注入：前端 / 服务端渲染场景，检查用户输入是否未转义直接输出。
2. 敏感信息硬编码
   - 搜索代码中是否有明文的密钥、密码、Token、数据库账号、API 密钥。
   - 检查是否把敏感信息直接打印到日志、控制台输出。
3. 输入校验缺失
   - 所有外部输入（用户输入、接口参数、文件内容）是否做了长度、格式、范围校验。
   - 避免「信任所有输入」的写法，AI 经常默认输入都是合法的。
4. 不安全的函数与 API
   - 例如 Python 的`eval()`、`exec()`、`pickle.load()`；C 语言的`strcpy()`、`sprintf()`等高危函数，确认是否有必要使用，有没有替代方案。
   - 文件操作场景检查路径遍历风险：是否校验了文件路径，避免`../`跳转到非预期目录。
5. 第三方依赖安全
   - 确认引入的第三方库是官方主流库，不是冷门或恶意包。
   - 避免使用版本不明、来源不明的依赖，防止引入已知漏洞。

## 四、性能与资源：避免低效与资源泄漏

AI 生成的代码通常「能用但低效」，尤其在处理数据量大的场景时问题明显。

1. 时间复杂度冗余
   - 检查是否存在不必要的嵌套循环，把 O (n) 就能解决的问题写成 O (n²)。
   - 循环内是否存在重复计算、重复查询数据库、重复 IO 操作。
2. 资源泄漏问题
   - 文件句柄、数据库连接、网络连接是否正确关闭，优先使用`with`、`try-finally`等自动释放机制。
   - 长驻进程场景检查内存泄漏：是否有持续增长的全局缓存、未销毁的对象。
3. 数据操作低效
   - 数据库查询是否存在 N+1 问题、全表扫描；大批量数据是否逐条插入而非批量写入。
   - 大文件处理是否一次性全部加载到内存，而不是流式读取。
4. 并发与线程安全
   - 多线程 / 多进程场景下，共享资源是否加锁，是否存在竞态条件。
   - 异步代码检查是否正确处理了 await，有没有协程泄漏、任务未捕获异常的问题。

## 五、工程质量层：可维护性与规范性

AI 生成的代码经常「一次性能用，但没法迭代维护」。

1. 代码结构合理性
   - 单个函数是否过长、职责是否单一，避免一个函数干所有事。
   - 模块划分是否清晰，有没有循环依赖、逻辑混乱的问题。
2. 命名可读性
   - 变量、函数、类名是否见名知意，避免大量无意义的`a`、`b`、`temp`、`func1`命名。
   - 命名风格是否统一，符合对应语言的规范（如 Python 的 snake_case、Java 的 camelCase）。
3. 魔法值与硬编码
   - 代码中直接出现的数字、字符串常量，是否提取为有意义的常量或配置项。
   - 避免业务规则硬编码在代码里，后续修改需要改源码。
4. 注释与文档
   - 核心逻辑、复杂算法是否有清晰注释，说明「为什么这么写」而不是重复代码内容。
   - 函数是否有参数、返回值、异常说明，关键入参的格式、取值范围是否明确。

## 六、大模型专属坑：AI 生成代码的高频问题

这是人工写代码很少犯、但 AI 特别容易踩的雷区。

1. API / 库幻觉
   - 对不熟悉的库 / 框架，一定要去官方文档核对：这个方法真的存在吗？参数名、参数顺序对吗？返回值结构是这样吗？
   - AI 经常编造不存在的参数、不存在的类方法，甚至整个不存在的第三方库。
2. 上下文遗忘
   - 对照你的原始要求，检查是否遗漏了你明确提出的约束（比如「必须用某某库」「不能用某某写法」「要兼容某某版本」）。
   - 长代码生成时，AI 经常前面说的规则后面就忘了，前后逻辑自相矛盾。
3. 过时 / 废弃语法
   - 检查是否使用了已经废弃的 API、旧版本写法，比如 Python 2 的语法、已弃用的旧版库函数。
   - 部分 AI 训练数据滞后，会给出早已不推荐的实现方式。
4. 想当然的业务逻辑
   - 涉及行业规则、业务流程、专业计算的部分，AI 很可能「凭感觉写」，看似合理实则不符合真实业务规则。
   - 涉及金额、时间、单位换算的逻辑务必人工验算，AI 经常搞错单位、精度、时区。
5. 开源合规风险
   - 大段生成的代码可能直接照搬了某开源项目的实现，若未遵循对应许可证可能存在版权风险。
   - 核心业务代码建议做开源片段比对，避免合规隐患。
