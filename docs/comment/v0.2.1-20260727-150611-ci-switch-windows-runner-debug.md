# v0.2.1 CI 切换 Windows Runner 决策记录

**时间**: 2026-07-27 15:06:11
**触发**: v0.2.1 CI/CD xvfb 修复推送后，CI 第四次运行依然 SIGABRT
**状态**: 已修复

## 问题描述

xvfb 修复后 CI 仍然在 `qapp` fixture 处 `Fatal Python error: Aborted`（退出码 134），
且这次连 `xvfb-run` 都没能阻止崩溃——说明问题不在 Xvfb 本身，而是 `xvfb-run` 的调用方式
或 CI 环境中的 xvfb 配置有问题。

## 根因分析

### 1. xvfb 方案理论上正确但实操有坑

xvfb 是 Linux 无头 Qt 测试的标准方案，但在 GitHub Actions 上使用 `xvfb-run` 有多个
陷阱：
- `xvfb-run` 需要 `xvfb` 包和 `xauth` 包，缺一不可
- 默认 `xvfb-run` 分配的 DISPLAY 可能和 pytest-qt 的 `QT_QPA_PLATFORM` 冲突
- pytest-qt 的 `qapp` fixture 在 CI 的 `setup` 阶段对 DISPLAY 极为敏感
- 调试困难：CI 日志不包含 xvfb 的 stderr，无法确定具体失败点

### 2. 根本矛盾：PySide6 桌面 GUI 在 Linux 无头环境上跑测试

本项目是 **PySide6 (Qt) Windows 桌面应用**，测试框架依赖 `pytest-qt`。
在 Linux 上跑 Qt 测试本质上是"跨平台兼容性测试"——需要额外维护 X11/Xvfb 基础设施，
且每次 PySide6 版本更新都可能引入新的 Linux 兼容性问题。

### 3. 投入产出比

为了在 Linux 上省一点 CI 额度，已经投入了 3 轮修复：
- libEGL 系统库
- libGL 系统库
- xvfb 虚拟显示

每次修复-推送-等待 CI 的周期约 15 分钟，且仍然没解决。

## 决策：切换到 windows-latest

### 理由

1. **原生支持**：PySide6 在 Windows 上原生支持 GUI 测试，无需任何虚拟显示层
2. **与开发环境一致**：本地开发环境是 Windows，CI 用 Windows 消除平台差异
3. **确定性**：`runs-on: windows-latest` 的 Qt 测试开箱即用，无需额外 apt 包
4. **项目定位**：本项目是 Windows 桌面应用，在 Windows 上测试最有意义

### 代价

- Windows runner 的 CI 额度消耗比 Linux 快（GitHub 免费额度中 Windows 按 2 倍计费）
- Windows runner 启动比 Linux 慢（约 30-60 秒额外延迟）

### 改进后的 workflow 要点

```yaml
runs-on: windows-latest
env:
  QT_QPA_PLATFORM: windows
  PYTHONFAULTHANDLER: 1
  QT_QUICK_BACKEND: software
```

- `QT_QPA_PLATFORM=windows`：显式指定 Qt 使用 Windows 平台插件
- `PYTHONFAULTHANDLER=1`：Python 崩溃时打印详细回溯
- `QT_QUICK_BACKEND=software`：Qt Quick 使用软件渲染（避免 OpenGL 依赖）

### 依赖安装简化

Linux 方案需要 3 个 apt 包 + xvfb-run；Windows 方案只需 pip install：

```powershell
pip install -r requirements-dev.txt
```

注意：`requirements-dev.txt` 包含 `-r requirements.txt`（PySide6 + httpx），
Windows 上 PySide6 自带所有运行时依赖，无需额外系统包。

## 后续建议

1. **CI 额度监控**：注意 GitHub Actions 免费额度用量，Windows runner 消耗更快
2. **release.yml 保持 windows-latest**：Release workflow 已经在用 windows-latest
3. **本地 CI 测试**：建议在本地 Windows 环境用 `act` 或其他工具模拟 CI 流程，减少远程调试次数
